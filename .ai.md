# Chronicle Sync — Foundry VTT Module

## Purpose

Bidirectional real-time sync between Chronicle and a Foundry VTT (v12-v14)
world, over REST + WebSocket.

## Architecture

```
module.mjs (entry point)
  └─ SyncManager (sync-manager.mjs)
       ├─ ChronicleAPI (api-client.mjs)    ← REST + WebSocket client
       ├─ JournalSync (journal-sync.mjs)   ← Entity ↔ JournalEntry
       ├─ MapSync (map-sync.mjs)           ← Map + markers/drawings/tokens/fog/layers ↔ JournalEntry (image page) with overlay
       ├─ CalendarSync (calendar-sync.mjs) ← Chronicle calendar date/events/world state; feeds the built-in calendar (calendar-bar.mjs)
       ├─ ShopWidget (shop-widget.mjs)     ← Chronicle shops as shop rooms in Foundry
       ├─ ItemSync (item-sync.mjs)        ← Actor inventory ↔ Chronicle relations
       ├─ SyncDashboard (sync-dashboard.mjs) ← ApplicationV2 window: Overview, Linked, Problems, Settings
       ├─ ActorSync (actor-sync.mjs)       ← Character entity ↔ Actor
       │    └─ generic-adapter.mjs          ← API-driven adapter (all systems)
       └─ CreatureSync (creature-sync.mjs) ← Creature page → NPC actor (Stamina/conditions back, if allowed)
```

### Data flow

1. GM starts Foundry → `module.mjs` initializes SyncManager.
2. `SyncManager.start()` validates config, initializes modules, connects WS.
3. WebSocket connects → initial sync (pulls mappings since `lastSyncTime`).
4. Live updates: WS messages routed to modules; REST for CRUD.
5. Foundry hooks detect local changes, push to Chronicle via REST.

`_syncing`-guard convention, real-time-calendar date-push guard, calendar
sub-resource display-only rule: see CLAUDE.md → Rules the code must keep.
`scripts/_realtime-date-guard.mjs` guards `CalendarSync.pushDate`, with a
one-time-per-session GM notice as a module-level singleton.

### Applied-date confirmation

Chronicle's sync chip distinguishes what Foundry *saw* (the `GET
/calendar/date` beacon) from what it *applied*.
`_applied-date-confirm.mjs`'s `confirmAppliedDate(api, {year, month, day})` →
`POST /calendar/date/confirm` is for the caller that applied a date to a
Foundry calendar, only after a real apply. A 404/405 (older Chronicle) is
tolerated and logged once per session. No Foundry calendar is integrated, so
nothing calls it yet (TODO(#95): the built-in calendar). `tools/test-applied-date-confirm.mjs`.

### Sync wire rules

- `sync-manager.mjs`'s `_onSyncStatus` reads `msg.status ?? msg.payload?.status`
  (emit shapes vary by message).
- Sync-state classifier `scripts/_calendar-sync-state.mjs` (`in-sync` /
  `date-drift` / `incompatible-structures` / `paused`) is unused until a
  Foundry calendar exists to compare against (TODO(#95)).
- Visibility toggles: `POST /entities/:id/reveal`, not a bare `PUT` (400s
  without a name).
- Item relations: flat `DELETE|PUT /relations/:relationId`, snake_case bodies.
- Chronicle calendar events: `isChronicleEventPublic` decides whether an event may be shown to every player (GM-only events, and `everyone` events with `visibility_rules`, may not). Fails closed. The players' calendar snapshot keeps only events it passes. `tools/test-calendar-sync-visibility.mjs`.

Pinned by `tools/test-sync-wire-fix.mjs`, `tools/test-calendar-sync-state.mjs`.

### Journals, catch-up and concurrency

- **Journal made in Foundry → Chronicle page.** `POST /entities` with a real `entity_type_id` (world setting `journalCreateTypeId`, chosen in Chronicle Sync's Settings under What syncs; unset means the campaign's first non-character type), then the text as `entry` in `PUT /entities/:id`, because Chronicle's create request has no text field. Journals owned by MapSync (`mapId` page flag or the Maps folder) or already linked to a calendar event (`calendarEventId` flag), and the old Chronicle Notes folder, are skipped. `_journal-create.mjs`, `_journal-ownership.mjs`; `tools/test-journal-create.mjs`.
- **Per-document guarding, no global flag.** Incoming Chronicle changes apply per entity id in arrival order (`_keyed-queue.mjs`); creates re-check for an existing journal inside the queue slot. Every write sync makes passes `syncOptions()` (a fresh `{chronicleSync: true}` per write, since Foundry 14 writes into the options it gets; `tools/test-sync-options.mjs`), and the create/update/delete hooks ignore only writes carrying it, so a GM edit during an apply still pushes. A journal whose create POST is in flight is remembered so the `entity.created` broadcast makes no second copy. `tools/test-journal-concurrency.mjs`.
- **Unsent local edit wins.** An incoming change for a journal with a debounced push pending is not applied; the stored `chronicleUpdatedAt` moves to the incoming version, the push goes out (Chronicle updates are partial) and the GM gets a warning.
- **Catch-up on connect.** `/sync/pull` is walked through `has_more` in 1000-row pages, each resuming just before the previous page's last `updated_at` (the server's `since` is strict and has no cursor) with repeats dropped by id (`_sync-pull-walk.mjs`); `lastSyncTime` is the first page's `server_time`, written only after the whole walk. The first sync latches `_initialSyncDone` only on success. `JournalSync.onInitialSync` runs the entity-list resync (changed pages, plus pages created in Chronicle since the last sync; an older page with no journal was deleted or never imported here and is not recreated; a first connect creates nothing) then sets aside journals whose page returns 404, only after a complete walk. Actor lists page via `walkEntityPages`. `tools/test-initial-sync-catchup.mjs`, `tools/test-journal-reconcile.mjs`.
- **Change feed.** Before modules apply, `SyncManager` reads Chronicle's `GET /sync/changes` from the saved `changeFeedCursor` (`{campaignId, seq, areas, createdAfter, types}`), at least 2.5 s after the socket opened because Chronicle holds back its newest 2 s of rows. A module with `feedArea` gets `{feed: {mode: 'delta', changes}}` when the cursor was saved while its area was syncing, else `{mode: 'full'}` (no cursor, another campaign's, `resetRequired`, or the area was off). The cursor is saved only when every feed area applied cleanly; replays are harmless. No feed (older Chronicle, a player's key) means a full rescan and no cursor. A module with `feedType` also gets `full` unless the cursor's `types` (what the server recorded when it was saved) include it. `ItemSync` (`feedType: 'relation'`) reconciles each listed character's whole inventory from `GET /entities/:id/relations` (add, adopt a Foundry item whose push has not recorded its relation yet, update quantity/equipped, unlink (never delete) items whose relation is not on that character, such as one removed in Chronicle or a copy dragged from another actor; nothing written when it already matches), serialized per actor; a new Foundry item that arrives carrying a relation flag is a copy, so it drops that flag and is pushed as its own relation; live `relation.*` messages do the same (`scripts/_inventory-plan.mjs`, `tools/test-inventory-plan.mjs`, `tools/test-item-feed.mjs`, `bench/items.bench.mjs`). `MapSync` (`feedType: 'marker'`) still reads `GET /maps` (Chronicle sends nothing for a map row) and refreshes the items of each map the feed names: fog by map id, markers, drawings, tokens and layers by finding the item among the GM cache and the stored page flags, every map once when one cannot be placed; a full catch-up refreshes no items, as before (`scripts/_map-feed.mjs`, `tools/test-map-feed.mjs`, `bench/maps.bench.mjs`). `ActorSync` refetches only listed characters that have a linked actor, skips actors at their version (the full walk does too), unlinks (keeps) the actor of a removed character, never creates actors at connect, and after a feed catch-up counts unlinked actors locally instead of listing Chronicle for the Issues nudge; a copy older than an actor's recorded version is ignored (`tools/test-actor-feed.mjs`, `bench/actors.bench.mjs`). `JournalSync` refetches only the listed pages: skip at the recorded version, create only for a page whose own `created_at` is after the cursor's `createdAfter` (the feed replays `created` entries; `createdAfter` moves only with the cursor, and a walk cut short keeps the old one), and set aside on `deleted` or a 404 after the usual checks. `scripts/_change-feed.mjs`, `tools/test-change-feed.mjs`, bench "a reopen reads only what changed".
- **Versions only move forward.** A journal's `chronicleUpdatedAt` is never set older than it is: an incoming copy older than it is ignored (an echo built before a later save), equal versions still apply (one-second precision). A permissions push is skipped when identical to the last one sent for that journal (`pushedPermissions`), and after a real one the module reads the page back for the version it stamped, because Chronicle's permissions save returns none and broadcasts the old one. `tools/test-journal-versions.mjs`.
- **Journal pushes** come from journal edits and from page create/edit/delete hooks (page text never fires `updateJournalEntry`), through the same per-journal debounce. A pulled sync mapping never creates a journal: the module only writes a mapping after making the journal, so a mapping without one means the GM deleted it here; the dashboard Resync brings it back on purpose. `tools/test-journal-page-edits.mjs`, `tools/test-journal-reconcile.mjs`, `bench/journals.bench.mjs`.
- **Claim ownership (Chronicle → Foundry).** When a linked character's Chronicle `owner_user_id` is applied (live update, create, or the connect/full-resync pass over cached `chronicleOwnerUserId` flags), the GM's client gives the mapped Foundry user (`userMappings`) OWNER on the actor (connect auto-matches a member to a Foundry user only when the name is unique among both members and Foundry users, since a mapping now grants an actor), inside `ActorSync._applyClaimOwnership` under `_syncing`; the write carries `chronicleSync` and `chronicleSyncApply`. `_claim-ownership-plan.mjs` (pure) returns `{grantUserId, staleOwnerUserIds, unmapped}`. Ownership is only ever added: on a hand-over from A to B, B gets OWNER, A keeps what they had and the GM gets one notice saying so; unclaiming changes nothing in Foundry; an owner with no live Foundry user changes nothing, gives one GM notice per session, and shows in Chronicle Sync's Settings under Players as a claimant with no Foundry user. A user who already has OWNER (or a GM) is skipped, so repeats write nothing. The other direction is unchanged: Foundry ownership reaches Chronicle only when the actor is first created (`_resolveOwnerUserId`); a later Foundry ownership change is not pushed. `tools/test-claim-ownership-plan.mjs`, bench `chr-claim-owner`.
- **Identity items (Chronicle → Foundry).** A pulled character whose `ancestry`, `culture`, `career` or `kit` differs from the actor's first embedded item of that type gets that item swapped, on the GM's client only, inside `ActorSync._updateActorFromEntity` / `_onCharacterCreated` under `_syncing`. Eligible fields are the field defs with `foundry_collection` + `foundry_item_single` and one `foundry_item_type` that is not class/subclass, and a key that is not `level`/`heroic_resource_name` (those stay Foundry-led). `_identity-item-plan.mjs` (pure) decides the swaps; `_identity-item-apply.mjs` finds an Item of that type and name (case-insensitive) in `game.items`, then Item compendiums (system packs first, index read with `fields: ['type']`), embeds it without `_id` and then removes the one item it replaces (other items of that type, such as a second kit, stay); with no match it embeds a `{name, type}` item flagged `chronicle-sync.chronicleMade`, filled from the campaign's own entry of that name when there is one (`GET /system-entries`, player view only): `system.description.value` gets the entry's text, details and trait list, and the flags record `entrySlug` and `entryUpdatedAt`. On later pulls, a sync-made item whose entry's `updatedAt` changed gets its text rewritten (`planEntryRefresh`); a description still holding GM-only content keeps the item name-only (`_campaign-entry-item.mjs`, `tools/test-campaign-entry-item.mjs`). Entries are read only when a field needs them, cached 30 seconds, and a 404 stops the reads for the session. An empty Chronicle value does nothing. Like scalar fields, the Chronicle value wins when it is applied, so an item swapped in Foundry while Chronicle still holds the older name is swapped back on the next pull. The writes carry `chronicleSync` and `chronicleSyncApply` so no item hook pushes them back; a failure leaves the sheet as it was and shows one GM notice. `tools/test-identity-item-plan.mjs`, bench `chr-identity-items`.
- **Actor pushes** are debounced per actor, take the mapped fields the edit touched (`_actor-field-diff.mjs`, adapter `toChronicleFieldsChanged`) and lay them over the entity's current `fields_data` before the PUT (`_putFieldsMerged`), because older Chronicle replaces the whole set on that route; a failed read pushes nothing. The name goes first with the stored version, then re-read `updated_at` after the fields PUT. `tools/test-actor-push.mjs`.

`calendar.event.*`, `calendar.date.advanced` → CalendarSync; `relation.*` →

`SyncManager._onSyncStatus` (fires one-time initial sync on first `connected`).

**Calendar blackout** — see the calendar rule in CLAUDE.md → "Rules the code
must keep". Date and event routes are live; the routes still answering `503
calendar_rebuilding` arm a self-clearing push pause only when the body says so.
Chronicle-side calendar changes arrive as `calendar.*` WS messages, routed in
`calendar-sync.mjs`.
Date-push refusals (400/422/403) pause date push once per session
(`_date-push-rejection.mjs`); `_apply-guard.mjs` is the per-note echo guard for
the built-in calendar's writes (TODO(#95)).

**Not yet handled:** `sync.error`, `sync.conflict`. Any other `calendar.*`
type logs one `console.debug` per type per session (`default:` branch).

**Calendar sub-resources** (`scripts/_calendar-subresources.mjs`): display-only,
no Foundry document writes. `calendar.structure.updated` only refetches
`GET /calendar`. No auto-created note on
`calendar.worldstate.changed` (no stable dedupe id to key a note on; the panel
and a GM chat line are the whole response). Weather reaches the dashboard
panel and a GM chat line. Announcements are GM whispers only
(`CalendarSync._announceToGM`) since Chronicle's `dm_only` gating is
server-side and re-broadcasting would leak it to players.
`tools/test-calendar-subresources.mjs`, `tools/test-calendar-subresource-routing.mjs`.

### Stashes

A "Stashes" button in the title bar of a Chronicle-linked character sheet
(players on characters they own in Foundry, the GM on all) opens the Stashes
window. Hidden when Chronicle has no stash routes or the Armory addon is off
(404 on the one probe).

- **Relay.** Only the GM client holds the API key. A player's window emits
  `stash:request` on `module.chronicle-sync`; the active GM
  (`game.users.activeGM`) is the only one that answers. The member acted for is
  `userMappings` looked up by the **sender id Foundry supplies as the socket
  listener's second argument**, never a payload field. No mapping, a character
  the sender does not own in Foundry, or no active GM each give a clear
  message. Socket traffic may reach every client, so each reply is
  encrypted to the asking window (ephemeral ECDH P-256 + AES-GCM,
  `_stash-crypto.mjs`); `recipients` is passed only as a best-effort extra.
  Replies/notices are honoured only from a GM sender. `stash:refresh` is a bare
  hint with no ids, so hidden characters' ids never reach players.
- **Request cards.** A message counts as a card only if a GM wrote it (players
  can create messages with the same markup); the move id is read from the
  flag, never the markup. Each pending request gets one whispered (GM-only) chat
  card with Approve / Turn down; the move id is in the message flags, which is
  how it is found again, deduplicated on startup/reconnect (`onInitialSync`
  fetches `GET /stashes/requests`), and rewritten to "Approved by X" / "Turned
  down by X" on `stash.settled` or a local press.
- **Refresh.** `stash.moved` / `stash.money_changed` re-pull the touched linked
  actors: `ActorSync.refreshFromChronicle` (the `entity.updated` path) then
  `ItemSync.refreshInventory` (the same whole-character reconcile as a
  `relation.*` message: adds, adopts, updates, unlinks; never deletes on its
  own). The one removal: after an APPLIED item move away from a character,
  the Foundry item linked to that moved item entity whose relation is gone,
  counting its `unlinkedRelationId` if the move's relation event unlinked it
  first (`_stash-reconcile.mjs`); events carry no item id, so they never
  delete.
- **Known limits.** Only the active GM answers, posts cards and refreshes; a
  second GM's window calls the API from its own client and needs its own API
  setup. "Character actor" is approximated as "carries a Chronicle `entityId`
  flag". Socket sender identity relies on Foundry passing the sender user id as
  the listener's second argument.
- **Live window.** `downtime.changed` and refresh notices reach open windows
  through the `chronicleStashChanged` hook, relayed to players over the socket.

## Security posture

Chronicle Sync trusts a single operator-configured Chronicle deployment, with
**targeted sanitization at the highest-risk surfaces**: stored HTML, `<img
src>` URLs, dashboard `innerHTML` interpolation. Response field shapes and WS
payload contents beyond the `type` allowlist are not validated.

### Auth surface separation — never cross

| Surface | Auth carrier | URL shape | Audience |
|---|---|---|---|
| REST API (sync) | `Authorization: Bearer ${apiKey}` header | `${apiUrl}/api/v1/campaigns/${campaignId}/...` | All sync modules, dashboard, wizard |
| WebSocket (sync) | `?token=${apiKey}` query param | `wss://...${apiUrl host}/ws?token=...&client=foundry-module` | `api-client.mjs::_doConnect` only |
| Module manifest fetch | Install-URL signed token in URL | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.json?token=...` | Foundry's update-check flow |
| Module zip download | Install-URL signed token in URL | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.zip?token=...` | Foundry's installer |
| Player notebook and calendar frames | The player's own notes grant (`cnt_…`), handed to the frame by `postMessage` at Chronicle's origin; kept in the client-scoped `notesGrants` setting keyed by Foundry user | `${apiUrl}/embed/campaigns/${campaignId}/notes/...` (the frame then calls `/api/notes-app/...`) | `player-notebook.mjs` only; never the GM's `apiKey` |

Different secrets, different validation paths — install-URL token is
Chronicle-signed with campaign+expiration claims `/api/v1/` rejects; `apiKey`
is a bearer token `module.json` rejects. Never consolidate them. Pinned by
`tools/test-api-client-security.mjs`.

### Trust posture

Each row is an unfixed-without-it footgun: a tampered Chronicle response could
otherwise reach a player's browser as XSS, a redirect-and-leak, a URL
break-out, or a leaked bearer token.

| Class | What we trust | What we validate | Where | Pin |
|---|---|---|---|---|
| HTML for `JournalEntry.text.content` | Chronicle's bluemonday UGCPolicy at write | Pre-sanitize via Foundry's `cleanHTML` (`foundry.utils` on v14, `TextEditor` before) at ingress | `scripts/_html-sanitizer.mjs` | `tools/test-html-sanitizer.mjs` |
| Pictures inside page text | Chronicle's own media path | Only `/media/<uuid>` (UUID-checked, so never a path) is copied; the signed link must be on the `apiUrl` host; raster MIME only, declared and served types must match; GM-only pictures are never copied | `scripts/picture-store.mjs`, `scripts/_inline-pictures.mjs` | `tools/test-inline-pictures.mjs` |
| Image URLs from map sub-resources | Operator-configured `apiUrl` host | `_isAllowedImageHost` rejects full-URL `image_url`/token `image` whose hostname doesn't match `apiUrl`, in `map-sync.mjs` + `map-viewer.mjs`; rejection → blank `<img>` + warning | `scripts/_url-validation.mjs` | `tools/test-url-validation.mjs` |
| User-visible DOM interpolation (e.g. dashboard test results) | Nothing | `replaceChildren` + `createTextNode`, never `innerHTML` of Chronicle data | `scripts/sync-dashboard.mjs::_renderTestResults` | `tools/test-sync-dashboard-xss.mjs` |
| Sync history rows (names, messages, people) | Nothing | Built as node descriptions; `toDom` sets only text and attributes | `scripts/_history-view.mjs::toDom` | `tools/test-history-view.mjs` |
| `campaignId` setting value | Operator typed it correctly | `_validateCampaignIdOrThrow` enforces UUID v4 shape before URL interpolation (`fetch`/`uploadMedia`) | `scripts/_settings-validation.mjs` | `tools/test-campaign-id-validation.mjs` |
| Outbound error log entries | Nothing (response body may echo the request) | `_scrubAuthHeaders` redacts `Bearer <token>` / `?token=<value>` before storing | `scripts/api-client.mjs::_scrubAuthHeaders` | `tools/test-api-client-secrets.mjs` |

**Sanitization layers on Chronicle HTML:** (1) Chronicle server-side bluemonday
UGCPolicy on write (primary); (2) Foundry ingress —
`_sanitizeIncomingHTML(html)` wraps Foundry's `cleanHTML`; every pulled page
goes through `JournalSync._pullHtml`, and `gm-secret-view.mjs` sanitizes the
GM-only content it shows (operator escape:
`skipIncomingSanitization`, default off); (3) Foundry render-time
`TextEditor.enrichHTML`, survives even if (1)+(2) fail. Static scan of every
ingestion site: `tools/test-html-sanitizer.mjs`.

**Descriptor schema integrity:** CI (`tools/check-package-descriptor.mjs`)
and runtime (`scripts/module.mjs::_runtimeValidateDescriptor`, GM-gated
`ready` hook, non-fatal `ui.notifications.error` on drift) share
`validateDescriptor(descriptor, moduleJson)`. `tools/test-descriptor-validator.mjs`.

**Auth quick reference:** API key is a Foundry **client** setting (CLAUDE.md →
Rules the code must keep), hidden from Foundry's settings list and entered in a
password field. Rate-limited
server-side (60 req/min default), campaign-scoped, optional
device-fingerprint lock. See also `chronicle/.ai/conventions.md` security
section and CLAUDE.md → "Working with this project" (tenets T-B1, T-B4).

**Module version header:** REST requests through `api-client.mjs` (`fetch`
and `uploadMedia`) send `X-Chronicle-Module-Version` from the manifest version
(`scripts/_module-version.mjs`); omitted if unreadable. Caller headers win. An
older Chronicle's CORS refuses the header, so a network TypeError on a request
that carried it retries once without it and drops it for the session. The
dashboard's raw connection probes never send it.
`tools/test-module-version-header.mjs`.

**Connect line:** the client-scoped `connectLine` setting takes
`chronicle://…/c/<campaignId>?key=…` (`chronicle+http://` for plain http),
parsed by `scripts/_connect-line.mjs`. `applyConnectLine` in `settings.mjs`
(GM only) writes `apiUrl`, `campaignId` and the client-scoped `apiKey`, then
clears the line; nothing changes on an invalid line. `SyncManager` reads the
settings in `start()` and is not restarted, so the GM reloads. Format in
API-CONTRACT.md → "Connect Line". `tools/test-connect-line.mjs`.

## Known Limitations

- Map drawings/tokens/fog/layers: read-only SVG overlays in `MapViewerSheet`;
  only markers are bidirectional.
- Calendar: the built-in calendar shows Chronicle's date, world state and
  events but is not Foundry's world clock; Foundry's own time does not move
  with it. Players see events for the current month and one either side.
- Shop rooms: arranging stays on the Chronicle shop page. A player who joins
  after the GM showed a shop sees it the next time the GM shows it. Players
  buy only while the GM is in the game and showing that shop, and only once
  the GM has matched their Foundry user to a Chronicle member. Other players'
  open rooms update their stock when the GM's room next refreshes, which
  also clears a basket they were filling. With two GMs, buying works only
  when the active GM is the one showing the shop.
- Shop items carry no image (`image_path` is null; Chronicle entities use
  Font Awesome icons, `shop-room-window.mjs`). Full sync runs only for GM users.
- PF2e character sync: only HP and name sync back (rest derives from items/rules).
- Custom system character sync needs `foundry_path` annotations on character
  preset fields, else the generic adapter returns null; every system, dnd5e and pf2e
  included, goes through the one generic adapter. System matching is fully
  API-driven via each installed system's `foundry_system_id`.
- Conflict handling: `ConflictError` (409, stale `expected_updated_at`)
  resolved per `conflictResolution`: `chronicle` (re-pull), `foundry` (force
  push), `newest` (compare timestamps).

Tests: `tools/test-permission-sync.mjs`, `tools/test-build-ownership.mjs`,
`tools/test-pc-claiming.mjs`, plus the per-module suites in `TESTING.md`.

## Chronicle Integration — Install & Updates

Foundry installs/updates this module from **Chronicle**, not GitHub: the
`foundry_vtt` sub-plugin serves each campaign a signed per-campaign install
URL that serves whichever version the campaign owner's update choice gives
(update automatically, ask first, or stay on one version). Chronicle pulls each
version from this repo's **GitHub releases** (or GitHub's source zip if a
release has no attached asset) — releasing means publishing a GitHub release
tagged e.g. `0.1.30`; nothing is uploaded to Chronicle by hand.

**Install flow:** the owner copies the install URL from the campaign's
Manage → Foundry page → Chronicle issues a signed manifest URL
(`/api/v1/campaigns/{id}/foundry-vtt/module.json?token={signed}`) → pasted
into Foundry's Install Module dialog → Foundry GETs it, gets `module.json`
with `manifest`/`download` rewritten to Chronicle URLs → follows `download`,
installs → Foundry stores that manifest URL and reuses it for future update
checks.

**`chronicle-package.json`** (repo root) is the serving descriptor Chronicle's
`PostInstallHook` reads from the release zip: manifest file location
(`package.moduleJsonPath`), fields to rewrite (`serving.rewriteFields` —
`manifest`+`download`), URL shape, and whether signed tokens are required.
Absent/invalid → Chronicle falls back to hardcoded defaults. CI validates it
every push/PR (`tools/check-package-descriptor.mjs`); bumping
`module.json#/id` requires updating `chronicle-package.json#/package/id` in
the same commit (CI-enforced). Full contract: API-CONTRACT.md →
"Chronicle-served Module Distribution".

The on-disk `module.json`'s `manifest`/`download` deliberately still point at
GitHub (pre-rewrite values, so a directly-obtained zip still works and
`PackagesPlugin` can auto-pull releases) — don't "fix" these; `serving.rewriteFields`
does the rewrite at serve time.

**Update Source dialog** (`scripts/update-info.mjs`, Game Settings → Module
Settings → Chronicle Sync → Update Source): shows the install-time manifest
URL, classifies it (chronicle/github/unknown) via the locked regex
`/api/v1/campaigns/.../foundry-vtt/module.json`, plus a manual "Check
Chronicle for updates" button. Keep this file and `chronicle-package.json` in
sync if the URL shape changes. A GM-only, fire-and-forget startup probe
(`surfaceManifestRecoveryIfNeeded()` in `module.mjs`'s `ready` hook) re-checks
the URL once per session; on an `auth`-category result it shows a sticky
`ui.notifications.error` telling the GM to reinstall — other outcomes stay
silent (covered by the manual dialog or not GM-actionable).

**Error classification** (`update-info.mjs`), in priority order: trust
Chronicle's `body.category` when it's one of the five wire-contract values
(`auth | config | not_found | validation | internal`); else HTTP-status
fallback (401/403→auth, 404→not_found, 5xx/else→internal); else Foundry-only
`network` (fetch threw) / `parse` (bad JSON or missing `version`).

| Category | Triggered by | Icon | Hue |
|---|---|---|---|
| `auth` | `invalid_token`, 401/403 w/o body | `fa-key` | red |
| `config` | `no_package_registered`, `pinned_version_not_installed`, `token_not_initialized`, `no_version_available` | `fa-gear` | amber |
| `not_found` | `campaign_not_found`, 404 w/o body, no install-time URL recorded | `fa-magnifying-glass` | amber |
| `validation` | `descriptor_invalid` | `fa-triangle-exclamation` | amber |
| `internal` | `module_json_missing`, `ErrInternal`, 5xx w/o body | `fa-server` | red |
| `network` | fetch threw (DNS/TLS/CORS/firewall) | `fa-plug-circle-xmark` | slate |
| `parse` | bad JSON, 200 OK missing `version` | `fa-file-circle-question` | slate |

Category names are snake_case on the wire, mirrored in CSS classes
(`result-auth`, `result-not_found`, ...). No local lookup table — the dialog
trusts `body.category` rather than duplicating Chronicle's mapping. Canonical
codes: API-CONTRACT.md → "Chronicle-served Module Distribution" → "Error code
catalog".

**Token rotation:** owner-rotated; old token immediately returns `403
invalid_token/auth`. No in-place repair — recovery is uninstall + reinstall
via a fresh install URL. The version pin survives rotation.

**Releases:** Actions → Release → Run workflow with the version (X.Y.Z).
`.github/workflows/release.yml` tags main and publishes the release with
generated notes and no attachments. Chronicle installs the source zip on Check
now (Admin → Packages), and its install hook writes the tag into `module.json`, so the
`version` on main is never read.

## Foundry conventions and footguns

- **ApplicationV2 `actions` only delegates `click`.** Non-click
  events must be wired directly in `_onRender` via `addEventListener`; adding
  them to the `actions` map is silently dropped, no error.
- **Test bootstrap for `foundry.applications.api` files.** Importing
  `calendar-sync.mjs` (or anything pulling `settings.mjs` →
  `update-info.mjs`) from a unit test throws
  `ReferenceError: foundry is not defined`; stub
  `globalThis.foundry/game/Hooks` before the dynamic `import()`. Canonical
  stub: `tools/test-calendar-sync-visibility.mjs`.
- **i18n key collisions are silent.** Two `registerMenu` calls can't
  share an i18n key (Foundry returns the first match), and a menu's keys can't
  reuse a setting's namespace. The menus use `CHRONICLE.SettingsWindow.Menu*`
  and `CHRONICLE.Settings.UpdateInfo.*`.
- **Handlebars helpers need explicit registration.** `eq`, `neq`, `lt`,
  `json` and `timeAgo` are registered in `module.mjs`'s `init`
  hook; register new ones alongside them.
- **ApplicationV2 PARTS templates need exactly one root element.**
  `_parsePartHTML` rejects a template rendering more or fewer than one root,
  only at `app.render()` time — and the failing branch depends on which
  `{{#if}}` path fires. Wrap the whole template body in one root element so
  every branch emits exactly one. CI guard: `tools/test-template-roots.mjs`
  (recurses every branch, asserts max-root-count == 1).
- **`lang/en.json` can't mix a dotted-flat key with a sibling
  literal-key string.** `expandObject` throws writing a property onto a
  string when both `parent.X = "..."` and `parent.X.Y = "..."` exist as
  siblings, and **rejects the entire lang file** — every `CHRONICLE.*` key
  then renders raw, with no error at lint time. Fix: nest the option set
  under a sibling key (e.g. `VisibilityOption: {Visible, Hidden, Secret}`),
  keep the field label flat. CI guard: `tools/test-lang-expand.mjs`.
- **JournalSync skips JournalEntries owned by another sync domain.** A
  journal with no `entityId` flag is pushed as a new page, so JournalSync skips
  `isCalendarNoteJournal(journal)` (linked to a calendar event by our
  `calendarEventId` flag), `isOldNotesJournal(journal)` (`_notes-folder.mjs`)
  and `isMapJournal(journal)`, as `_isHandledByActorSync` does for characters.
  Tested at `tools/test-calendar-note-journal.mjs`.

## Architectural Decision Log

### A-1: Chronicle-served module distribution
Release artifacts are served by Chronicle on a per-campaign signed URL, not
GitHub Releases or Foundry's Package Repository — lets the operator pin
different campaigns to different versions and control rollout from
Chronicle's admin UI, without exposing unbounded public install URLs.

### A-2: Descriptor-driven Chronicle serving
Chronicle reads `chronicle-package.json` from the release zip to learn how to
serve this module, falling back to hardcoded defaults if absent — keeps
Chronicle generic so any future Foundry module can register its own
descriptor without Chronicle code changes.

### A-3: Foundry stores the Chronicle URL post-install; updates loop back to Chronicle
Foundry's install flow stores the per-campaign manifest URL locally and
always checks it for updates, never GitHub — keeps the campaign owner's
version pin authoritative. Risk: Foundry's Package Repository also lists this
module under its GitHub URL and may prompt to switch (README's "Updating").

### A-4: Update Source dialog is a manual check, not an autopatcher
It's a diagnostic, not part of the runtime update loop — Foundry's native
Update All is the production path, and auto-correcting a deliberately
GitHub-installed instance would be too aggressive.
