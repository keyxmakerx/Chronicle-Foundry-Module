# Chronicle Sync — Foundry VTT Module

## Purpose

The Chronicle Sync module for Foundry VTT enables bidirectional real-time sync
between a Chronicle instance and a Foundry VTT game world. It runs as a Foundry
v12-v14 module, connecting via REST API + WebSocket to the Chronicle backend.

## Architecture

```
module.mjs (entry point)
  └─ SyncManager (sync-manager.mjs)
       ├─ ChronicleAPI (api-client.mjs)    ← REST + WebSocket client
       ├─ JournalSync (journal-sync.mjs)   ← Entity ↔ JournalEntry
       ├─ MapSync (map-sync.mjs)           ← Map + markers/drawings/tokens/fog/layers ↔ JournalEntry (image page) with overlay
       ├─ CalendarSync (calendar-sync.mjs) ← Calendar events/date ↔ Calendaria/SimpleCalendar
       ├─ ShopWidget (shop-widget.mjs)     ← Shop entity inventory in Foundry UI
       ├─ NoteSync (note-sync.mjs)        ← Chronicle Notes ↔ JournalEntry
       ├─ ItemSync (item-sync.mjs)        ← Actor inventory ↔ Chronicle relations
       ├─ SyncDashboard (sync-dashboard.mjs) ← 8-tab ApplicationV2 status/management UI
       └─ ActorSync (actor-sync.mjs)       ← Character entity ↔ Actor
            └─ generic-adapter.mjs          ← API-driven adapter (all systems)

scripts/update-info.mjs                    ← Diagnostic dialog for the Chronicle-served install/update flow
chronicle-package.json (repo root)          ← Serving descriptor consumed by Chronicle's `foundry_vtt` sub-plugin
tools/check-package-descriptor.mjs          ← CI script that validates the descriptor against module.json
```

### Data Flow

1. **GM starts Foundry** → `module.mjs` initializes SyncManager
2. **SyncManager.start()** → validates config, initializes modules, connects WS
3. **WebSocket connects** → performs initial sync (pulls mappings since `lastSyncTime`)
4. **Live updates** → WS messages routed to modules; REST for CRUD operations
5. **Bidirectional** → Foundry hooks detect local changes, push to Chronicle via REST

### Sync Guard

All sync modules use a `_syncing` boolean flag to prevent infinite loops:
- Set `true` before applying a remote change to Foundry
- Foundry's change hooks fire but see `_syncing === true` → skip pushing back
- Reset to `false` after the change is applied

### Real-time calendar date-push guard (RC-4, FM-REALTIME-DATE-SIGNAL)

`GET /calendar/date` carries `tracks_real_time` — the composed
`UsesRealTime()` predicate (`syncapi/calendar_api_handler.go:95`); `GET
/calendar` never does. When true, Chronicle's calendar is wall-clock
authoritative, so the module treats dates as **read-only**: it pauses only
its own `PUT /calendar/date` pushes (pull and event sync are untouched).
`scripts/_realtime-date-guard.mjs` centralizes this so `calendar-sync.mjs`'s
three hook-triggered pushes (`_onCalendariaDateTimeChange`,
`_onLocalDateChange`, `_onSimpleCalendarDateChange`) and
`sync-dashboard.mjs`'s manual push button (`_onPushDate`) share one
implementation: a fetch-before-push `GET` re-run on every push attempt (push
is rare enough that the round trip is cheap, and it self-heals a mid-session
flag flip — never trust a cached value alone), plus treating a `PUT` 422 as
the identical condition (Chronicle's W3 write guard), never a retryable sync
error. The one-time-per-session GM notice is a module-level singleton shared
by both files, mirroring the structure guard's session-scoped state
(`calendar-sync.mjs`'s `_calendarSyncDisabled`, ~line 327) but without tying
the flag to either class instance. Tested at
`tools/test-realtime-date-signal.mjs`.

### Applied-date confirmation (FM-SYNC-CONFIRMED-DATE)

Pairs with a parallel Chronicle-side change (C-SYNC-APPLIED-BEACON) that lets
Chronicle's sync chip distinguish what Foundry *saw* (the `GET
/calendar/date` beacon) from what it actually *applied* to the local
calendar module. `calendar-sync.mjs`'s `_setLocalDate` — the single choke
point both apply paths funnel through (the poll path, `onInitialSync`'s
`GET /calendar` fetch on connect/reconnect, and the WebSocket-driven path,
`_onChronicaleDateAdvanced` on `calendar.date.advanced`) — now returns a
`Promise<boolean>` reporting whether a real local calendar-module setter ran
without throwing (Calendaria `setDateTime`/legacy `setDate`, or SimpleCalendar
`setDate`, now awaited). Neither calendar module's setter returns an
inspectable success signal, so "no throw" is the strongest available proxy —
flagged as a stop-and-flag rather than invented. Both call sites POST
`scripts/_applied-date-confirm.mjs`'s `confirmAppliedDate(api, {year, month,
day})` → `POST /calendar/date/confirm` ONLY when `_setLocalDate` resolves
`true` — never on a bare fetch, never on apply failure. The confirm call runs
after `_setLocalDate`'s `_syncDepth` guard has already unwound (it only sends
an outbound POST to Chronicle; it triggers no Foundry hooks, so it cannot
re-enter the push handlers' `_syncing` checks). A 404/405 (older Chronicle
without the endpoint) is tolerated via a session-singleton debug-log-once,
mirroring the RC-4 guard's shared-singleton pattern above. Tested at
`tools/test-applied-date-confirm.mjs`.

### Sync wire fixes (FM-SYNC-WIRE-FIX-R1)

Five defects that made sync silently not work, fixed together. All
module-side; the endpoints/behaviors they target already existed on Chronicle.

1. **Initial sync never fired (FM-SYNC-1).** `api-client.mjs` emits
   `sync.status` UNWRAPPED — `_emit('sync.status', {status:'connected'})`, and
   `_emit` fans the object straight to listeners — but the `sync.manager`
   listener read only `msg.payload?.status`, so the guard was never true.
   `_performInitialSync` (the full `/sync/pull` since epoch, every module's
   `onInitialSync`, the journal duplicate-deletion post-pass) and the reconnect
   resync (gated on the never-set `_initialSyncDone`) were BOTH dead on every
   world. Fix is on the LISTENER — now `_onSyncStatus(msg)` reads
   `msg.status ?? msg.payload?.status` — not the emit, because client emit
   shapes are intentionally inconsistent (`sync.retryComplete` uses `{payload}`)
   and the same object feeds the wildcard router. Pinned:
   `tools/test-sync-wire-fix.mjs` (fix 1).
2. **SimpleCalendar skipped the structure guard.** `onInitialSync`'s
   mismatch guard was `_calendarModule === 'calendaria'`-only; a SimpleCalendar
   world fell through to `_setLocalDate` and wrote Chronicle's coordinates into
   a structurally-incompatible calendar. Added
   `_readActiveSimpleCalendarStructure()` (SC's `getCurrentCalendar()` →
   `numberOfDays`/`weekdays`, with a `getAllMonths`/`getAllWeekdays` fallback)
   and a `_readActiveFoundryStructure()` dispatcher; the guard now covers both
   paths and still fails OPEN on an unreadable structure. This guard is hot
   BEFORE fix 1 in history (it must be, so revived initial sync can't date-jump
   an unguarded SC world). Pinned: `tools/test-sync-wire-fix.mjs` (fix 2).
3. **Dishonest sync badge.** The dashboard computed "In Sync" from raw y/m/d
   equality and drove "paused" from a flag the SC path never set. Replaced with
   a pure four-state classifier `scripts/_calendar-sync-state.mjs`
   (`in-sync` · `date-drift` w/ direction · `incompatible-structures` w/ counts
   · `paused`); the dashboard feeds it the live module's pause flag AND its own
   structure comparison, so an incompatibility surfaces even when the module
   failed open. Pinned: `tools/test-calendar-sync-state.mjs`.
4. **Visibility toggle 400'd.** Dashboard single + bulk visibility toggles PUT
   `/entities/:id` with only `{is_private}` → Chronicle's UpdateEntity requires
   a name → 400 (swallowed). Routed to `POST /entities/:id/reveal`
   (ToggleEntityReveal, accepts exactly `{is_private}`). Pinned:
   `tools/test-sync-wire-fix.mjs` (fix 4).
5. **Item relations used nonexistent paths + wrong casing.** `item-sync.mjs`
   DELETE/PUT used nested `/entities/:id/relations/:relId[/metadata]` (404) and
   the create body was camelCase with a null target. Chronicle serves flat
   `DELETE|PUT /relations/:relationId` and binds snake_case
   `target_entity_id`/`relation_type`/`reverse_relation_type` (requiring a
   target). Fixed paths + body (snake_case, object metadata not a JSON string);
   relation-create now SKIPS when the item has no linked Chronicle entity (a
   custom item has no target to relate to — logged once, not per item). Pinned:
   `tools/test-sync-wire-fix.mjs` (fix 5).

**Disclosures (shipped, not silent):**
- Fix 1 activates code that has NEVER run on any world (full `/sync/pull` since
  epoch, every `onInitialSync`, the journal duplicate-deletion pass). Worlds
  with pre-existing synced data must be tested, not only fresh worlds.
- Drifted worlds visibly date-jump on first load post-fix (plus a confirm
  beacon). Expected.
- **Follow-up (not done here):** Calendaria back-catalog note mappings live in

### Calendar sub-resources (FM-SYNC-SUBRESOURCES-P1, 2026-07-25)

**Decision: P1 is display-level and non-destructive.** No sub-resource handler
writes into a Foundry document. Three specific abstentions, each deliberate:

1. **No structure auto-apply on `calendar.structure.updated`.** Rewriting the
   Foundry calendar's months/weekdays from a broadcast is the most destructive
   write available to this module: Calendaria stores notes against month/day
   coordinates, so re-shaping the calendar silently re-dates every note in the
   world. The handler re-compares and badges instead. Non-destructive
   auto-merge is a later arc (calendar-remodel requirements §1 item 10).
2. **No auto-created celestial note on `calendar.worldstate.changed`.** The
   payload carries no celestial detail and no stable event id, so a
   re-broadcast or reconnect would create duplicate notes with nothing to
   dedupe on. Announcing what the payload contains is honest; inventing a
   "Meteor Shower" note from a mood tint is not.
3. **No speculative Calendaria weather setter.** Calendaria publishes weather
   READS; no shipped build exposes a documented setter. The module probes
   `setWeather` / `setCurrentWeather` / `setWeatherForDate` and degrades to a
   GM chat line, with the probe result mirrored into the diagnostics bundle so
   a build that does expose one shows up in an operator's bug report.

**Decision: announcements are GM whispers, never public chat.** Chronicle gates
dm_only traffic server-side (`Message.RequiresDM`, `internal/websocket/hub.go`),
but "cleared for the GM" is not "cleared for the table" — weather zones and
world state routinely encode what the DM is holding back. Re-broadcasting would
launder a server-side permission decision into a player-visible one, the leak
class cordinator#32 hardened against. `CalendarSync._announceToGM` whispers to
the GM user ids and is the module's only chat surface.

**Decision: structure signals are processed while paused.** `onMessage` routes
them ahead of the `_calendarSyncDisabled` guard, because fixing the calendar in
Chronicle — the documented remedy for a mismatch pause — is precisely what emits
the broadcast. Behind the guard, a pause would survive its own cause until a
world reload, the same dead-on-arrival shape FM-SYNC-WIRE-FIX removed from
initial sync. This is also the only path that can CLEAR a mismatch pause.

**Chronicle-side gap: `calendar.worldstate.changed` never reaches the wire.**
Three blockers, all Chronicle-side, verified against `main` 2026-07-25 — see
API-CONTRACT.md → "Gap: `calendar.worldstate.changed` never reaches the wire"
for the full trace. In short: the publisher adapter in `internal/app/routes.go`
has no `case` for it (so it hits `default: return` before the bus), the payload
carries no celestial detail, and `GET /calendar/world-state` is not on the
syncapi group. The module handler ships wired and tested; it lights up when
Chronicle closes blocker 1.

## Security posture

This section consolidates the security invariants this module relies on after FM-SEC Phase 4 (audit: `cordinator/reports/foundry/2026-05-22-fm-security-audit.md`; chunks #52, #53, #54, #55, #56, #57, #58).

### For humans

Chronicle Sync trusts a single Chronicle deployment that the operator configures. The trust posture is **targeted sanitization at the highest-risk surfaces** (FM-SEC §0.5 D1=(c)) — we do not validate every Chronicle response field, but we hard-gate the three surfaces where a compromised Chronicle could harm a Foundry client: stored HTML (M-3), `<img src>` URLs (M-2), and `innerHTML` interpolation in the dashboard (M-1). The descriptor schema gets BOTH a CI check AND a runtime re-check (Chunk 7) so silent drift surfaces immediately.

Two auth surfaces exist and **never cross**: the per-campaign `apiKey` for `/api/v1/...` traffic (REST + WS), and the install-URL signed token for the `/foundry-vtt/module.json` + zip download endpoints (manifest fetch only). The chronicle#323 wire-contract drift was caught at this seam — the regression-pin tests in Chunk 6 keep that drift from recurring.

### Auth surface separation (chronicle#323 lesson)

| Surface | Auth carrier | URL shape | Audience |
|---|---|---|---|
| REST API (sync) | `Authorization: Bearer ${apiKey}` header | `${apiUrl}/api/v1/campaigns/${campaignId}/...` | All sync modules, dashboard, wizard |
| WebSocket (sync) | `?token=${apiKey}` query param | `wss://...${apiUrl host}/ws?token=...&client=foundry-module` | `api-client.mjs::_doConnect` only |
| Module manifest fetch | Install-URL signed token in URL | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.json?token=...` | Foundry's update-check flow (not us — Foundry's installer reads the URL) |
| Module zip download | Install-URL signed token in URL | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.zip?token=...` | Foundry's installer |

The lesson from chronicle#323: a refactor on either side that "consolidates" the two tokens (e.g., uses `apiKey` for manifest fetch, or install-URL token for `/api/v1/`) breaks both. Reasoning: the install-URL token is signed by Chronicle's per-campaign signing key and includes campaign + expiration claims that `/api/v1/` doesn't accept; the `apiKey` is a long-lived bearer token that `/foundry-vtt/module.json` won't accept. They're different secrets with different validation paths.

**Pinned by:** `tools/test-api-client-security.mjs` (Chunk 6) — asserts every REST method sends Bearer, asserts WS connect uses `?token=` and never Bearer, asserts no `/syncapi/` substring anywhere.

### Trust posture (FM-SEC §0.5 D1=(c))

Chronicle is operator-controlled but treated as a hostile-content-broker for three classes of data:

| Class | What we trust | What we validate | Where |
|---|---|---|---|
| HTML for `JournalEntry.text.content` | Chronicle's bluemonday UGCPolicy at write (C-SEC §1.3) | Pre-sanitize via `TextEditor.cleanHTML` at ingress (defense-in-depth) | `scripts/_html-sanitizer.mjs` |
| Image URLs from map sub-resources | Operator-configured `apiUrl` host | Reject full-URL `image_url` / token `image` whose hostname doesn't match `apiUrl` | `scripts/_url-validation.mjs` |
| User-visible DOM interpolation | Nothing — we never trust Chronicle strings as HTML in our own UI | DOM construction via `replaceChildren` + `createTextNode` (no `innerHTML` interpolation of Chronicle data) | `scripts/sync-dashboard.mjs::_renderTestResults` |
| `campaignId` setting value | Operator typed it correctly | UUID v4 shape (8-4-4-4-12 hex) before any URL interpolation | `scripts/_settings-validation.mjs` |
| Outbound error log entries | Nothing (Chronicle's response body may echo our request) | Scrub `Bearer <token>` and `?token=<value>` before storing in the recent-errors ring buffer | `scripts/api-client.mjs::_scrubAuthHeaders` |

What we DON'T validate:
- Field shapes on Chronicle responses (`entity.name: string`, `entity.tags: array`). The blanket-validation option (D1=(b)) was considered and rejected; implementation cost was high and the operator-controlled-Chronicle threat model didn't justify it.
- The contents of WebSocket payloads beyond the `type` allowlist — once `type` matches a known prefix, the handler trusts the payload shape.

### Sanitization layers

Three-layer defense on Chronicle HTML reaching a player's browser:

1. **Chronicle server-side (primary).** bluemonday UGCPolicy at the service layer, 8 plugins. Verified in `cordinator/reports/chronicle/2026-05-22-c-security-audit.md §1.3`. Runs on WRITE — `EntryHTML` is sanitized before it's stored in Chronicle's database.
2. **Foundry-side ingress (defense-in-depth, Chunk 3).** `_sanitizeIncomingHTML(html)` wraps Foundry's `TextEditor.cleanHTML` and runs at six ingestion sites in `journal-sync.mjs` + `note-sync.mjs`. Catches a Chronicle regression that bypasses layer 1, an old DB entry that pre-dates a rule strengthening, or a hand-edit that skips the service layer. Operator escape: `skipIncomingSanitization` setting (default off = sanitization on).
3. **Foundry render-time.** `TextEditor.enrichHTML` runs on every render of a `JournalEntry.text.content`. This is Foundry's stock defense and survives even if layers 1 + 2 both fail (e.g., a hand-edited page in a release zip).

**Pinned by:** `tools/test-html-sanitizer.mjs` (Chunk 3) — static-source scan asserts every `entity.entry_html` / `note.entry_html` ingestion site is wrapped by `_sanitizeIncomingHTML`. A new ingestion path that bypasses the sanitizer fails CI.

### Descriptor schema integrity (Chunk 7)

`chronicle-package.json` is Chronicle's source-of-truth for HOW to serve this module: where the manifest lives inside the zip, what URL shape to emit, whether per-campaign signing is required. The Chronicle backend reads it via a `PostInstallHook` with a documented fallback to hardcoded defaults if the file is absent or malformed (the **D3 silent fallback** — Chronicle prefers degraded-but-functional serving over a hard error).

Two validators run the same `validateDescriptor(descriptor, moduleJson)` function:
- **CI** (`tools/check-package-descriptor.mjs`): runs on every PR via `.github/workflows/check-descriptor.yml`. Adds an on-disk existence check for `package.moduleJsonPath` (CI-only concern).
- **Runtime** (`scripts/module.mjs::_runtimeValidateDescriptor`): GM-gated, called from the `ready` hook. Fetches the deployed descriptor + module.json, runs the same validator. Surfaces a sticky `ui.notifications.error` on drift; non-fatal.

This means a release zip with a malformed descriptor that bypassed CI (hand-edit, ad-hoc deployment) is caught on the GM's first world load, not after silent drift accumulates.

**Pinned by:** `tools/test-descriptor-validator.mjs` (Chunk 7) — static-source pin that BOTH call sites import the shared `validateDescriptor`. T-O4 single-source-of-truth invariant.

### Auth-surface quick reference (the chronicle#323 invariants)

- API key stored as a Foundry **client** setting (this browser only; FM-SEC-KEY-SCOPE 2026-09-06 — it was world-scoped, which every connected player could read via `game.settings.get`), masked as a password input via `Hooks.on('renderSettingsConfig', ...)` in `settings.mjs`; `migrateApiKeyToClientScope()` moves a legacy world value across and deletes the world document
- REST uses `Authorization: Bearer <key>` header — never `?token=` query
- WebSocket uses `?token=<key>` query param (browsers don't allow setting headers on the WS upgrade) — never `Authorization`
- Module-manifest fetch uses install-URL signed token in the URL — a different secret from `apiKey`
- Per-key rate limiting enforced server-side (60 req/min default)
- Campaign-scoped: `apiKey` can only access its bound campaign
- Device fingerprint binding: optional one-time device lock (Chronicle-side)

## Known Limitations

- **Map drawings/tokens/fog/layers**: Managed by Chronicle's web map editor only.
  Not synced to Foundry. Only markers (pins) sync as Foundry Scene Map Notes
- **SimpleCalendar events**: Limited — events managed as journal notes, no CRUD hooks
  (the structure-mismatch guard now covers the SC path too, FM-SYNC-WIRE-FIX)
- **Shop icon field**: Always returns null (`shop-widget.mjs:146`)
- **Single scene**: Only the active Foundry scene syncs (no multi-scene)
- **GM only**: Full sync runs only for GM users; players get passive updates via Foundry
- **Character sync: limited fields back from PF2e**: Only HP and name sync from Chronicle to PF2e actors (most values are derived from items/rules)
- **Character sync: custom system requirements**: Custom game systems must include `foundry_path` annotations on their character preset fields for bidirectional sync. - **System matching**: Fully API-driven. `_detectSystem()` queries `/systems` and matches by `foundry_system_id` from each system's manifest. Any installed system package with a `foundry_system_id` is automatically detected.

## Chronicle Integration — Install & Updates

This module's release artifacts are distributed by **Chronicle**, not by GitHub
Releases. Chronicle's `foundry_vtt` sub-plugin serves each campaign a signed,
per-campaign install URL pinned to whichever version the campaign owner picked.

### Install flow

1. Campaign owner pins a version (or leaves auto-latest) in Chronicle's
   campaign settings → **Foundry VTT** disclosure.
2. Chronicle generates a signed per-campaign manifest URL:
   `/api/v1/campaigns/{campaign_id}/foundry-vtt/module.json?token={signed}`.
3. Owner copies the URL; user pastes into Foundry's **Install Module** dialog.
4. Foundry GETs the URL — Chronicle responds with the resolved version's
   `module.json` with `manifest` + `download` fields rewritten to per-campaign
   Chronicle URLs (instead of the GitHub URLs in the source `module.json`).
5. Foundry follows `download` to fetch the zip; extracts; module installed.
6. Foundry stores the install-time manifest URL and uses it for every future
   update check — so updates always come from Chronicle.

### How Chronicle knows how to serve this module

`chronicle-package.json` at repo root is the **serving descriptor**, and it is
the **contract between this repo and Chronicle's `packages` plugin**. Every
Foundry-specific serving assumption Chronicle would otherwise hardcode lives
in this one file, so the same Chronicle code can serve this module or any
future Foundry module without changes on Chronicle's side.

Chronicle's `PostInstallHook` (added in C-FMC-5b) reads it from the extracted
release zip to learn:

- Which JSON file in the zip is the manifest (`package.moduleJsonPath`).
- Which fields to rewrite on serve (`serving.rewriteFields` — currently
  `manifest` + `download`).
- What URL shape to emit (`serving.manifestEndpoint`, `serving.downloadEndpoint`).
- Whether per-campaign signed tokens are required.

If the descriptor is absent or invalid in a particular release zip, Chronicle
falls back to hardcoded defaults equivalent to the current descriptor. The
descriptor is the "Foundry instructs Chronicle" surface — Foundry-specific
serving knowledge lives here, not hardcoded in Chronicle.

CI validates the descriptor on every push and PR via
`tools/check-package-descriptor.mjs` (run by
`.github/workflows/check-descriptor.yml`). Bumping
`module.json#/id` (rare) requires updating `chronicle-package.json#/package/id`
in the same commit, and CI enforces this.

For the full URL contract — request shapes, response shapes, error codes —
see `API-CONTRACT.md` → "Chronicle-served Module Distribution".

### Why `module.json`'s `manifest` and `download` fields still point at GitHub

The on-disk `module.json` keeps its GitHub URLs in `manifest` and `download`.
These are the **pre-rewrite** values; Chronicle overrides them on serve. They
serve two purposes:

1. If anyone obtains the source zip directly (not via Chronicle), they get
   sane, working defaults pointing at GitHub Releases.
2. Chronicle's `PackagesPlugin` uses the GitHub URLs to auto-pull new releases
   into its catalog.

Do **not** "fix" these to Chronicle URLs in the source `module.json`. The
descriptor's `serving.rewriteFields` array is what wires the rewrite at serve
time.

### Update Source diagnostic dialog

`scripts/update-info.mjs` provides a per-install diagnostic at
**Game Settings → Module Settings → Chronicle Sync → Update Source**:

- Surfaces the install-time manifest URL Foundry stored.
- Classifies it (chronicle / github / unknown) so the operator can confirm
  whether the install is wired up to Chronicle's per-campaign endpoint.
- Manual "Check Chronicle for updates" button hits the install-time URL
  directly so the operator can confirm reachability and inspect the response.

The Chronicle classifier regex is the locked URL shape
(`/api/v1/campaigns/.../foundry-vtt/module.json`). If Chronicle's URL shape
ever changes, update both `update-info.mjs` and `chronicle-package.json` in
the same commit.

#### Passive recovery probe on startup

`scripts/module.mjs`'s `ready` hook fires `surfaceManifestRecoveryIfNeeded()`
(GM-only, fire-and-forget) right after `syncManager.start()`. The helper
hits the install-time manifest URL once, reuses the same `categorize()`
classification the manual check uses, and if the result is `auth`
category (Chronicle 403 with `body.category: "auth"`, or any 401/403
without a Chronicle body) it surfaces a sticky `ui.notifications.error`
with Chronicle's `body.message` (or a localized fallback) instructing the
GM to reinstall from a fresh URL. Non-`auth` outcomes are intentionally
silent — they're either non-actionable from the GM's seat (`config`,
`internal`) or covered by the dialog when the GM opens it manually
(`network`, `parse`, `not_found`).

Why GM-only: only GMs can reinstall a module in Foundry. Surfacing the
prompt to players would be noise without recovery.

Why one-shot: the banner is sticky (`{permanent: true}`) so it persists
until the GM dismisses or fixes the install. Re-probing on every refresh
would either spam or require deduplication state with no real benefit.

#### How errors are classified

When the manual check fails, the dialog renders a 4-clause diagnostic
(*what we tried / what happened / likely cause / what to do*) tagged with
one of seven error categories — Chronicle's five server-side buckets plus
two Foundry-only fallback buckets for failures Chronicle never sees.

Categorization order (`scripts/update-info.mjs:104-110`):

1. **Trust Chronicle's `body.category`** when the response carries one of
   the five values in the wire-contract enum (`auth | config | not_found
   | validation | internal`). Chronicle classifies server-side; Foundry
   does not second-guess it. The five-value enum is pinned by cordinator
   `decisions/2026-05-17-error-catalog-wire-contract.md`.
2. **HTTP-status fallback** when `body.category` is absent or
   unrecognized: 401 / 403 → `auth`, 404 → `not_found`, 5xx → `internal`,
   anything else → `internal`. Covers proxy / CDN errors and Chronicle
   releases that add a new category before Foundry's enum is updated.
3. **Foundry-built fallback** for failures that never reach Chronicle:
   `network` (fetch threw) and `parse` (response wasn't JSON, or 200 OK
   was missing the `version` field). The precondition "no install-time
   URL recorded" reuses the `not_found` category with a client-built
   4-clause.

| Category     | Source                                  | Triggered by                                                                                | Icon (FontAwesome)         | CSS hue |
|--------------|-----------------------------------------|---------------------------------------------------------------------------------------------|----------------------------|---------|
| `auth`       | Chronicle (`body.category`) or HTTP 401/403 | `invalid_token`, or any 401/403 without a Chronicle body                                | `fa-key`                   | red     |
| `config`     | Chronicle (`body.category`)             | `no_package_registered`, `pinned_version_not_installed`, `token_not_initialized`, `no_version_available` | `fa-gear`                  | amber   |
| `not_found`  | Chronicle (`body.category`) or HTTP 404 | `campaign_not_found`, or any 404 without a Chronicle body, or "no install-time URL recorded" precondition | `fa-magnifying-glass`      | amber   |
| `validation` | Chronicle (`body.category`)             | `descriptor_invalid` (release zip's `chronicle-package.json` failed Chronicle's schema check) | `fa-triangle-exclamation`  | amber   |
| `internal`   | Chronicle (`body.category`) or HTTP 5xx | `module_json_missing`, the catch-all `ErrInternal` wildcard, or any 5xx without a Chronicle body | `fa-server`                | red     |
| `network`    | Foundry-side                            | `fetch` threw before reaching Chronicle (DNS, TLS, CORS, firewall)                          | `fa-plug-circle-xmark`     | slate   |
| `parse`      | Foundry-side                            | JSON parse failed, or 200 OK with no `version` field                                        | `fa-file-circle-question`  | slate   |

The category names are snake_case on the wire — e.g. `not_found` is
spelled with an underscore, never a hyphen. CSS class names
(`result-auth`, `result-config`, `result-not_found`, etc.) mirror the
category strings exactly so the classifier output drops straight into
the template.

There is intentionally **no** code-to-category lookup table in
`update-info.mjs`. The classifier trusts `body.category` because (a)
Chronicle already classifies server-side and ships an actionable
`body.message`, (b) duplicating the mapping in Foundry creates the exact
cross-repo drift that PR #40 caught and FM-DRIFT-GUARD will mechanically
enforce. The canonical list of `error` codes lives in `API-CONTRACT.md`
→ "Chronicle-served Module Distribution" → "Error code catalog", which
mirrors `error-catalog.json` at the pinned Chronicle URL.

### Token rotation and recovery

The campaign owner can rotate their per-campaign token from Chronicle's
Foundry VTT disclosure in campaign settings. Rotation is **immediate** —
the old token returns `403 { "error": "invalid_token", "category":
"auth", "message": "..." }` from the moment the new one is issued.
Implications:

- **Already-installed Foundry instances** will start failing update checks
  on their next probe. Foundry's native "Check for Update" UI surfaces this
  as a generic failure; the Update Source dialog surfaces it as the
  `auth` category with an actionable "reinstall from a fresh URL" message
  rendered verbatim from `body.message`.
- **There is no in-place repair** — we don't have a supported way to swap
  out the install-time URL Foundry stored. Recovery is: campaign owner
  shares the new install URL, user uninstalls + reinstalls the module via
  that URL, Foundry stores the new URL, update checks resume.
- **The pin survives rotation.** Rotating a token does not change which
  module version is pinned; only the credential changes.

### The release workflow

`.github/workflows/release.yml` produces a release zip that includes
`chronicle-package.json` alongside `module.json`. The workflow's tag-push
trigger is currently disabled (the operator drives releases manually via
`workflow_dispatch`); Chronicle's `PackagesPlugin` auto-polls GitHub releases
and pulls anything it finds, so the publishing cadence is whatever the
operator chooses.

## Foundry conventions and footguns

Pinned here so future PRs don't re-learn lessons that bit earlier ones.
Each entry: short name, when it bit, the rule.

### F-PR2-1: ApplicationV2 `actions` only delegates `click`

Pointer events (`pointerdown`/`pointerenter`/`pointerup`), keyboard events,
and any non-`click` interaction must be wired directly in `_onRender` via
`element.querySelectorAll(...).addEventListener(...)`. Adding the event
name to the `actions` map is silently dropped — there is no error. PR 2's
drag-select and PR 3's moon-strip click both live in `_onRender`.

### F-PR2-2: Hook re-render preserves in-progress form state

Calendaria hooks (`dateTimeChange`, `noteCreated`, etc.) can fire mid-edit
and trigger an Application re-render. If the form's input values lived
only in the DOM they would be wiped. The pattern: write every input
keystroke to a class-side `_formData` (or equivalent) object via a
`#wireFormInputs` helper attached in `_onRender`; the next render reads
from `_formData`, not from DOM-side defaults. The 250 ms re-render
throttle in `#scheduleRerender` also helps.

### F-PR2-3: Test bootstrap for files that touch `foundry.applications.api`

Importing `scripts/calendar-sync.mjs` (or anything that transitively pulls
`settings.mjs` → `update-info.mjs` / `sync-calendar.mjs`) from a unit
test breaks with `ReferenceError: foundry is not defined` because those
files reference `foundry.applications.api` at module top level. Solution:
stub `globalThis.foundry`, `globalThis.game`, and `globalThis.Hooks`
before the dynamic `import()` call. See
`tools/test-calendar-sync-visibility.mjs` for the canonical stub block.

### F-PR2-4: i18n key collisions are silent

Foundry's i18n is a flat lookup with no namespace ownership. Two
`game.settings.registerMenu` calls cannot share an i18n key — Foundry
returns the first match silently. Convention: settings-menu entries
live under `CHRONICLE.Settings.<menuId>Menu.*`, never under
`CHRONICLE.Settings.<menuId>.*` (that namespace is the boolean toggle's).
PR 1 collided; PR 2 carry-in fix B renamed.

### F-PR3-1: Foundry Handlebars helpers must be registered explicitly

Handlebars itself ships no `json` helper. Foundry registers a small core
set, but `eq`, `neq`, `lt`, `gt`, `json`, `timeAgo`, etc. are all
module-registered in `scripts/module.mjs`'s `init` hook. When adding a
template that needs a new helper, register it alongside the existing
ones. PR 3 added `json` for stashing preset params in `data-*`
attributes.

### F-PR3-2: Calendaria's `conditionTree` root must be a group

A `conditionTree` whose root is not `{type: 'group', mode, children}` is
silently ignored by Calendaria's matcher — the note never fires. The
operator sees no error. The pure validator in
`scripts/sync-calendar-condition-builder.mjs` catches this; the form's
save path blocks on `Errors.RootMustBeGroup`,
`Errors.EmptyGroup`, and `Errors.NotAnObject`.

### F-PR3-4: ApplicationV2 PARTS templates must render exactly one root HTML element

Foundry's `_parsePartHTML` (foundry.mjs:32135) rejects any `static PARTS`
template whose rendered output contains more than one root HTML element
— or zero — with `Error: Template part 'X' must render a single HTML
element.` Foundry catches this only at app render time; the JSON parses,
the Handlebars compiles, the app object instantiates fine. The crash
fires on `app.render()`.

Worst part: the failure mode depends on which branch of `{{#if}}/{{else}}`
fires. PR 3's `sync-calendar.hbs` had a `degraded` branch that emitted
one `<section>` (clean) and an `else` branch that emitted three siblings
(`<header>`, `<main>`, `<footer>`) — the app worked in degraded mode
during PR 3 dev (no Calendaria connected, so the degraded branch fired)
and crashed the moment the operator opened it against a real Calendaria.

Same footgun class as F-LANG-1 (silent Foundry-runtime contract that
Node tests can't catch by accident). Fix: wrap the entire template body
in a single root element (e.g. `<div class="sync-calendar-root">`) so
EVERY branch — degraded, year-view, month-view, with or without import
banner — emits exactly one root. **CI guard at
`tools/test-template-roots.mjs`** statically analyzes every PARTS-
registered template across the repo, recurses through every
`{{#if/unless/each/with}}` branch, and asserts max-root-count == 1.

### F-CAL-RAIL-SCROLL: the single-root wrapper must be a height-constrained flex column

Consequence of F-PR3-4. The mandated `<div class="sync-calendar-root">` wrapper
sits between `.sync-calendar-content` (a `height:100%` flex column) and the
header/grid/footer. If the wrapper keeps the default `display:block`, the grid's
`flex:1 1 auto` and the left rail's `overflow-y:auto; min-height:0` have nothing
to resolve against, so the validation **findings panel overflows and visually
overlaps** instead of scrolling (reported as "errors bottom-left I can't read").
Fix (in `styles/chronicle-sync.css`): `.sync-calendar .sync-calendar-root {
display:flex; flex-direction:column; height:100%; min-height:0; }`. Any new
ApplicationV2 single-root wrapper that contains a `flex:1` scroll region needs
the same treatment.

### F-LANG-1: `lang/en.json` cannot mix dotted-flat keys with sibling literal-key strings

Foundry's `Localization._loadTranslationFile` runs the parsed JSON
through `expandObject`, which walks dotted keys as nested paths. If a
sibling key sets `parent.X = "some string"` AND another sibling sets
`parent.X.Y = "..."` (dotted-flat form), `_expand` tries to write a
property on the string and throws `TypeError: Cannot create property
'Y' on string '...'`. **Foundry rejects the entire lang file** — every
`CHRONICLE.*` key renders raw across the whole module.

Worst part: the failure is silent at lint time. The JSON parses fine.
It only blows up at Foundry boot, and Foundry's console message points
at the file, not the offending key pair.

PR 2 introduced the pattern (`Visibility` + `Visibility.Visible/Hidden/Secret`,
ditto `DisplayStyle`). The note-form labels were rendering raw for the
whole PR 2 → PR 3 window; nobody noticed because the operator wasn't
using event-create heavily. PR 3's empty-state import banner made the
breakage visible. Fix: nest the option set inside a sibling key
(`VisibilityOption: {Visible, Hidden, Secret}`), keeping the field
label `Visibility` as a flat string. **CI guard at
`tools/test-lang-expand.mjs`** simulates `expandObject` and fails loud
on any future collision (both string-vs-object and
duplicate-after-expansion paths).

### F-PR3-3: Sync Calendar editor reaches Chronicle via the public api surface

The Sync Calendar Application does NOT hold a direct reference to the
SyncManager. It looks up the Chronicle REST client through
`game.modules.get('chronicle-sync').api.getAPI()` (the public surface in
`module.mjs:307`). Same pattern external integrators use. Avoids
tight-coupling the editor to SyncManager lifecycle.

### F-SYNC-1: JournalSync must skip JournalEntries owned by another sync domain

`JournalSync`, `NoteSync`, and `CalendarSync` all listen on the same global
`createJournalEntry` hook, and `JournalSync` is registered first (`module.mjs`).
**Calendaria stores every note as a `JournalEntry`** (flagged
`flags.calendaria.isCalendarNote`, in a "Calendar Notes" folder), SimpleCalendar
does too, and `NoteSync` stores Chronicle Notes as JournalEntries. `JournalSync`
used to push **every** new journal lacking an `entityId` flag to `POST /entities`
with `entity_type_id: 0`. The Chronicle server resolves `0` to the campaign's
*first* entity type (`syncapi/api_handler.go` `CreateEntity`) — almost always
"Character" — so the notes showed up in the **Characters** list.

The trigger in the wild: **Calendaria auto-seeds a calendar's `festivals` as
note JournalEntries** the first time the calendar activates
(`festivals/festival-manager.mjs` → `NoteManager.createNote`). A *Calendar of
Therin* with holidays ("Day of Rebirth", "Eve of the Dead", "Haelyn's Day", …)
silently spawned that many "Character" entities. See **`CALENDARIA-INTEGRATION.md`**
for the full Calendaria data model (verified against upstream source).

Rule: before pushing a journal as an entity, `JournalSync` skips it when
`isCalendarNoteJournal(journal)` (exported from `calendar-sync.mjs`; matches the
calendar module's own note flag — `flags.calendaria.isCalendarNote/isCalendarJournal`
or the SimpleCalendar scopes — present on the very first create hook) or
`_isHandledByNoteSync(journal)` is true. Mirrors the existing
`_isHandledByActorSync` guard; same class as the actor duplicate problem that
`cleanupActorJournalDuplicates` cleans up.

Cascade + actor-pull traps when cleaning up the bad entities: the mis-pushed
note's JournalEntry still carries the bogus `entityId` flag, so deleting the
entity in Chronicle broadcasts `entity.deleted`, which
`JournalSync._onEntityDeleted` turns into a **delete of the calendar note in
Foundry** (Calendaria does NOT block this for a GM — `note-manager.mjs`
`onPreDeleteJournalEntry` only protects festival notes from non-GMs). And simply
unlinking the journal without deleting the entity leaves an orphan that
`ActorSync.onSyncMapping` will re-pull as a festival-named Actor. Correct order:
unlink the journal locally **first**, then delete the entity server-side — the
one-off macro in `CALENDARIA-INTEGRATION.md` does exactly this.

Guard logic is unit-tested at `tools/test-calendar-note-journal.mjs`.

## Architectural Decision Log

This section records non-obvious architectural choices so future contributors
don't re-litigate them. Each entry: decision, why, what was rejected, when.

### A-1: Chronicle-served module distribution (FM-CSU, PRs #34 + #35, May 2026)

**Decision.** This module's release artifacts are served by Chronicle on a
per-campaign signed URL, not by GitHub Releases or Foundry's central Package
Repository.

**Why.** The operator wanted to pin different campaigns to different module
versions, control rollout from Chronicle's admin UI, and not expose unbounded
public install URLs.

**Rejected.** (a) GitHub Releases as the install source — no per-campaign
pinning, no rollout control. (b) Foundry's central Package Repository — same
problems, plus we'd need to keep the in-repo `module.json` URLs synced with
whatever the Package Repository surfaces (drift risk). (c) Embedding Foundry
serving knowledge in Chronicle's core — operator's modularity principle:
*"foundry stuff inside chronicle natively just makes a redundant mess."*

### A-2: Descriptor-driven Chronicle serving (FM-PKG-DESCRIPTOR, PR #35)

**Decision.** Chronicle reads `chronicle-package.json` from the extracted
release zip to learn how to serve this module — manifest path, fields to
rewrite, URL templates, token requirements. Falls back to hardcoded defaults
if the descriptor is absent.

**Why.** Keeps Chronicle generic — any future Foundry module (or other package
type) can register its own descriptor without modifying Chronicle. The
"Foundry instructs Chronicle" pattern.

**Rejected.** (a) Hardcoding Foundry-specific paths and rewrites in Chronicle.
(b) Inline metadata in `module.json` flags — Foundry's release workflow uses
`jq` to rewrite `module.json`, which would risk clobbering a `flags.chronicle`
block. (c) Per-Chronicle-instance config — punts the problem; operator would
have to keep two configs in sync.

### A-3: Foundry stores Chronicle URL post-install; updates loop back to Chronicle

**Decision.** Foundry's install flow stores the per-campaign manifest URL
locally; subsequent update checks always hit Chronicle (per-campaign signed
URL), never GitHub.

**Why.** The pinned version is owned by Chronicle. Round-tripping update
checks through Chronicle means the campaign owner's version choice is
authoritative.

**Risk + mitigation.** Foundry's central Package Repository also lists this
module with its GitHub manifest URL. On update check, Foundry may prompt to
switch the locally-stored manifest URL to the Package Repository's — see
README's "Updating in Foundry" section.

### A-4: Update Source diagnostic dialog as a manual check

**Decision.** Surface a manual "Check Chronicle for updates" dialog in the
module settings rather than autopatching the install URL or running update
probes on a timer.

**Why.** The dialog is a diagnostic tool, not part of the runtime update
loop. Foundry's native Setup → Modules → Update All is the production update
path. The dialog answers the operator's "is this install wired up correctly?"
question without touching Foundry's stored URLs.

**Rejected.** Auto-correcting the install-time URL — too aggressive; if the
operator deliberately installed from GitHub for some reason, we shouldn't
silently re-point them.
