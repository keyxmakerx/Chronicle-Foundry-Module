# Chronicle Sync: Foundry VTT Module

Bidirectional real-time sync between Chronicle and a Foundry VTT (v12-v14)
world, over REST + WebSocket. Wire contract: API-CONTRACT.md. Tunable values:
CONSTANTS.md. Live checks: TESTING.md. Cross-cutting rules: CLAUDE.md →
"Rules the code must keep" (per-write sync guard, real-time calendar date guard,
display-only calendar sub-resources, calendar blackout).

## Architecture

```
module.mjs (entry point)
  └─ SyncManager (sync-manager.mjs)
       ├─ ChronicleAPI (api-client.mjs)    ← REST + WebSocket client
       ├─ JournalSync (journal-sync.mjs)   ← Entity ↔ JournalEntry
       ├─ MapSync (map-sync.mjs)           ← Map + markers/drawings/tokens/fog/layers ↔ JournalEntry (image page) with overlay
       ├─ CalendarSync (calendar-sync.mjs) ← Chronicle calendar date/events/world state; feeds the built-in calendar (calendar-bar.mjs)
       ├─ ShopWidget (shop-widget.mjs)     ← Chronicle shops as shop rooms in Foundry
       ├─ ItemSync (item-sync.mjs)         ← Actor inventory ↔ Chronicle relations
       ├─ SyncDashboard (sync-dashboard.mjs) ← ApplicationV2 window: Overview, Linked, Problems, Settings
       ├─ ActorSync (actor-sync.mjs)       ← Character entity ↔ Actor
       │    └─ generic-adapter.mjs         ← API-driven adapter (all systems)
       └─ CreatureSync (creature-sync.mjs) ← Creature page → NPC actor (Stamina/conditions back, if allowed)
```

Data flow: GM's `ready` → `SyncManager.start()` validates config, initializes
modules, connects the WebSocket → initial sync (mappings since `lastSyncTime`,
then the change feed) → live: WS messages route to modules, Foundry hooks push
local changes over REST.

1. GM starts Foundry → `module.mjs` initializes SyncManager.
2. `SyncManager.start()` validates config, initializes modules, connects WS.
3. WebSocket connects → initial sync (pulls mappings since `lastSyncTime`).
4. Live updates: WS messages routed to modules; REST for CRUD.
5. Foundry hooks detect local changes, push to Chronicle via REST.

Per-write echo marking, real-time-calendar date-push guard, calendar
sub-resource display-only rule: see CLAUDE.md → Rules the code must keep.
`scripts/_realtime-date-guard.mjs` guards `CalendarSync.pushDate`, with a
one-time-per-session GM notice as a module-level singleton.

### Applied-date confirmation

Chronicle's sync chip distinguishes what Foundry *saw* (the `GET /calendar/date`
beacon) from what it *applied*. `confirmAppliedDate(api, {year, month, day})` in
`_applied-date-confirm.mjs` posts `POST /calendar/date/confirm` only after a real
apply; 404/405 (older Chronicle) is tolerated and logged once per session. No
Foundry calendar is integrated, so nothing calls it yet (TODO(#95)).
`_calendar-sync-state.mjs` (`classifyCalendarSyncState`: paused > structure
mismatch > date drift > in-sync, fails open) is likewise unused until then.

### Sync wire rules

- `_onSyncStatus` reads `msg.status ?? msg.payload?.status` (emit shapes vary).
- Visibility toggles: `POST /entities/:id/reveal`, not a bare `PUT` (400s without a name).
- Item relations: flat `DELETE|PUT /relations/:relationId`, snake_case bodies.
- Calendar events: `isChronicleEventPublic` decides whether a player may see an event (GM-only events, and `everyone` events with `visibility_rules`, may not); fails closed; the players' snapshot keeps only events it passes.

Pinned by `tools/test-sync-wire-fix.mjs`, `test-calendar-sync-state.mjs`, `test-calendar-sync-visibility.mjs`.

### Journals, catch-up and concurrency

- **Journal made in Foundry → Chronicle page.** `POST /entities` with a real `entity_type_id` (world setting `journalCreateTypeId`, chosen in Chronicle Sync's Settings under What syncs; unset means the campaign's first non-character type), then the text as `entry` in `PUT /entities/:id`, because Chronicle's create request has no text field. Journals owned by MapSync (`mapId` page flag or the Maps folder) or already linked to a calendar event (`calendarEventId` flag), and the old Chronicle Notes folder, are skipped. `_journal-create.mjs`, `_journal-ownership.mjs`; `tools/test-journal-create.mjs`.
- **Per-document guarding, no global flag.** Incoming Chronicle changes apply per entity id in arrival order (`_keyed-queue.mjs`); creates re-check for an existing journal inside the queue slot. Every write sync makes passes `syncOptions()` (a fresh `{chronicleSync: true}` per write, since Foundry 14 writes into the options it gets; `tools/test-sync-options.mjs`), and the create/update/delete hooks ignore only writes carrying it, so a GM edit during an apply still pushes. A journal whose create POST is in flight is remembered so the `entity.created` broadcast makes no second copy. `tools/test-journal-concurrency.mjs`.
- **Who sends a change.** Every client's hooks fire for every change and sync runs on GM clients only. A GM's own change is sent by that GM's client; a player's change to a linked journal, actor or inventory is sent by the active GM's client (`sendsChangeHere` in `_change-author.mjs`), so it is not lost and a later pull cannot write Chronicle's older value back over it. With no GM in the game a player's change is not sent.
- **A player's change needs Chronicle's say-so.** It goes out under the GM's key, and a player who owns a document can rewrite its link flags, so the link alone is never trusted. A character change is sent only when Chronicle's `owner_user_id` is the member the player is matched to (`userMappings`); a quantity or equipped change also needs the relation to be in that character's list; a journal edit needs custom visibility with an `edit` grant covering that member in `GET /entities/:id/permissions`, never carries sharing, and sends no text when the journal or the Chronicle page holds GM-only text (the GM's client would put that text back around markup a player wrote). A refused change stays in Foundry and the GM is told once per document. A character change that is sent names the member (`actingUserId` on `PUT /entities/:id/fields`), and Chronicle judges it as that member: the picks it will not take (an off-list or Directors-only class, a typed-in name on a limited step, an emptied required step, an ask-first pick) come back as `held` with a reason and are left out of Chronicle; the player's item stays in Foundry, nothing is written back, and the GM gets one notice per distinct refusal per actor (`_player-picks-held.mjs`, `ActorSync._tellHeld`). A burst that mixes a GM's and a player's edit is judged as the player's. A player's own creates and deletes are sent without asking, by the active GM's client: a new journal becomes a page, a new actor a character, and any link flag on a document a player creates is cleared first (it would aim later pushes at someone else's page). A journal or actor delete is sent only when Chronicle says the player owns it (an edit grant on the page, or `owner_user_id` is their member) and the page's name is the document's name; Chronicle moves it to its Trash, so it is restorable. A new item on a character that is theirs is sent as a "Has Item" link, but only to a page players can already view (`playersCanView`: not private, default visibility or a public/all-players grant), never to a hidden one. Anything that is not theirs (another character's item added or removed, a page they cannot edit deleted) becomes a whispered GM card ("Mira added Rope to Sela", Send to Chronicle / Not now; `_player-asks.mjs`, `player-asks.mjs`, `player-asks-chat.mjs`). The ids behind a card are player-writable flags, so on Send the GM's client re-reads the pages they name and re-checks the same rules; a name that differs from the card's shows the real names and needs a second press. A message is a card only if a GM wrote it. Removing an item from a character they own still asks the GM (`_remote-deletes.mjs`), because Chronicle's relation delete has no Trash. `tools/test-change-author.mjs`, `test-player-picks-held.mjs`, `test-journal-player-edit.mjs`, `test-item-player-change.mjs`, `test-player-asks.mjs`, `test-player-create-delete.mjs`, bench "a player's HP edit" and `bench/player-asks.bench.mjs`.
- **A copy is unlinked.** A journal or actor created already carrying another document's Chronicle link (Foundry's Duplicate, a compendium import, a drag from another world) has the link flags removed, so two documents never push to one page; the journal copy then becomes its own page like any new journal. A copied creature actor drops its creature link the same way. Bench "a duplicated journal".
- **Clearing a journal's text** sends `entry: null`, since Chronicle reads an empty string as "leave the text alone"; a journal with no text page sends nothing for `entry`.
- **Unsent local edit wins.** An incoming change for a journal with a debounced push pending is not applied; the stored `chronicleUpdatedAt` moves to the incoming version, the push goes out (Chronicle updates are partial) and the GM gets a warning.
- **Catch-up on connect.** `/sync/pull` is walked through `has_more` in 1000-row pages, each resuming just before the previous page's last `updated_at` (the server's `since` is strict and has no cursor) with repeats dropped by id (`_sync-pull-walk.mjs`); `lastSyncTime` is the first page's `server_time`, written only after the whole walk. The first sync latches `_initialSyncDone` only on success. `JournalSync.onInitialSync` runs the entity-list resync (changed pages, plus pages created in Chronicle since the last sync; an older page with no journal was deleted or never imported here and is not recreated; a first connect creates nothing) then sets aside journals whose page returns 404, only after a complete walk. Actor lists page via `walkEntityPages`. `tools/test-initial-sync-catchup.mjs`, `tools/test-journal-reconcile.mjs`.
- **Change feed.** Before modules apply, `SyncManager` reads Chronicle's `GET /sync/changes` from the saved `changeFeedCursor` (`{campaignId, seq, areas, createdAfter, types}`), at least 2.5 s after the socket opened because Chronicle holds back its newest 2 s of rows. A module with `feedArea` gets `{feed: {mode: 'delta', changes}}` when the cursor was saved while its area was syncing, else `{mode: 'full'}` (no cursor, another campaign's, `resetRequired`, or the area was off). The cursor is saved only when every feed area applied cleanly; replays are harmless. No feed (older Chronicle, a player's key) means a full rescan and no cursor. A module with `feedType` also gets `full` unless the cursor's `types` (what the server recorded when it was saved) include it. `ItemSync` (`feedType: 'relation'`) reconciles each listed character's whole inventory from `GET /entities/:id/relations` (add, adopt a Foundry item whose push has not recorded its relation yet, update quantity/equipped, unlink (never delete) items whose relation is not on that character, such as one removed in Chronicle or a copy dragged from another actor; nothing written when it already matches), serialized per actor; a new Foundry item that arrives carrying a relation flag is a copy, so it drops that flag and is pushed as its own relation; live `relation.*` messages do the same (`scripts/_inventory-plan.mjs`, `tools/test-inventory-plan.mjs`, `tools/test-item-feed.mjs`, `bench/items.bench.mjs`). `MapSync` (`feedType: 'marker'`) still reads `GET /maps` (Chronicle sends nothing for a map row) and refreshes the items of each map the feed names: fog by map id, markers, drawings, tokens and layers by finding the item among the GM cache and the stored page flags, every map once when one cannot be placed; a full catch-up refreshes no items, as before (`scripts/_map-feed.mjs`, `tools/test-map-feed.mjs`, `bench/maps.bench.mjs`). `ActorSync` refetches only listed characters that have a linked actor, skips actors at their version (the full walk does too), unlinks (keeps) the actor of a removed character, and makes the actor for a character whose own `created_at` is after `createdAfter` (the full walk uses the previous `lastSyncTime`; a first connect makes none; one list of the character types picks the new characters out of the feed's `created` entries; an actor the GM deleted here, keeping the page, put the page on `syncExclusions` and is not made again; `_actor-catch-up.mjs`, `tools/test-actor-catch-up.mjs`). Create, update and catch-up work for one character run in turn (`ActorSync._inTurn`). After a feed catch-up counts unlinked actors locally instead of listing Chronicle for the Issues nudge; a copy older than an actor's recorded version is ignored (`tools/test-actor-feed.mjs`, `bench/actors.bench.mjs`). `JournalSync` refetches only the listed pages: skip at the recorded version, create only for a page whose own `created_at` is after the cursor's `createdAfter` (the feed replays `created` entries; `createdAfter` moves only with the cursor, and a walk cut short keeps the old one), and set aside on `deleted` or a 404 after the usual checks. `scripts/_change-feed.mjs`, `tools/test-change-feed.mjs`, bench "a reopen reads only what changed".
- **Versions only move forward.** A journal's `chronicleUpdatedAt` is never set older than it is: an incoming copy older than it is ignored (an echo built before a later save), equal versions still apply (one-second precision). A permissions push is skipped when identical to the last one sent for that journal (`pushedPermissions`), and after a real one the module reads the page back for the version it stamped, because Chronicle's permissions save returns none and broadcasts the old one. `tools/test-journal-versions.mjs`.
- **Journal pushes** come from journal edits and from page create/edit/delete hooks (page text never fires `updateJournalEntry`), through the same per-journal debounce. A pulled sync mapping never creates a journal: the module only writes a mapping after making the journal, so a mapping without one means the GM deleted it here; the dashboard Resync brings it back on purpose. `tools/test-journal-page-edits.mjs`, `tools/test-journal-reconcile.mjs`, `bench/journals.bench.mjs`.
- **Claim ownership (Chronicle → Foundry).** When a linked character's Chronicle `owner_user_id` is applied (live update, create, or the connect/full-resync pass over cached `chronicleOwnerUserId` flags), the GM's client gives the mapped Foundry user (`userMappings`) OWNER on the actor (members are matched to Foundry users by `_member-match.mjs`, since a mapping grants an actor: first the GM's own setup, a member whose linked character's actor exactly one player owns or has as their assigned character; then the same name ignoring case; then the same name ignoring spacing, punctuation and accents; a name only when unique on both sides, and never a Foundry user already linked to another member. Matching runs at connect, again when a Foundry user is created, renamed or given a character and when a link changes, and, at most every two minutes, after re-reading members when a claimant has no Foundry user; each re-match applies claims at once through `reconcileOwnership`. A player none of that links can link themselves with a code from Chronicle (`player-link.mjs`). `tools/test-member-match.mjs`, bench `fvtt-player-added-later`), inside `ActorSync._applyClaimOwnership`; the write carries `chronicleSync` and `chronicleSyncApply`. `_claim-ownership-plan.mjs` (pure) returns `{grantUserId, staleOwnerUserIds, unmapped}`. Ownership is only ever added: on a hand-over from A to B, B gets OWNER, A keeps what they had and the GM gets one notice saying so; unclaiming changes nothing in Foundry; an owner with no live Foundry user changes nothing, gives one GM notice per session, and shows in Chronicle Sync's Settings under Players as a claimant with no Foundry user. A user who already has OWNER (or a GM) is skipped, so repeats write nothing. The other direction is unchanged: Foundry ownership reaches Chronicle only when the actor is first created (`_resolveOwnerUserId`); a later Foundry ownership change is not pushed. `tools/test-claim-ownership-plan.mjs`, bench `chr-claim-owner`.
- **A player with no hero gets the one they claimed.** The connect catch-up only makes actors for characters made since the last sync, so an older claimed hero with no actor (a GM's unimported page a new player claims, or a claim made before the player was linked) is brought in by its claim instead: when its claimant is linked to a live non-GM Foundry user who owns no actor of the hero type and has no assigned character, and sync is on for the page. Claims come from a live `entity.updated` on a character with no actor, from each member's `character_entity_id` in `GET /members` at connect and on every `reconcileOwnership` (a link made, a user added or renamed), and from live claims that waited for their claimant's link this session. Making the actor is a pull, so `reconcileOwnership` skips it unless characters take changes from Chronicle. When a claim gives a player OWNER and they have no assigned character (or it points at a deleted actor), the actor becomes their character; one the GM assigned is never changed. `_player-hero.mjs`, `tools/test-player-hero.mjs`, bench `chr-claim-brings-hero`.
- **Identity items (Chronicle → Foundry).** A pulled character whose `ancestry`, `culture`, `career`, `kit` or `complication` (Draw Steel) differs from the actor's first embedded item of that type gets that item swapped, on the GM's client only, inside `ActorSync._updateActorFromEntity` / `_onCharacterCreated`. Eligible fields are the field defs with `foundry_collection` + `foundry_item_single` and one `foundry_item_type` that is not class/subclass, and a key that is not `level`/`heroic_resource_name` (those stay Foundry-led). `_identity-item-plan.mjs` (pure) decides the swaps; `_identity-item-apply.mjs` finds an Item of that type and name (case-insensitive) in `game.items`, then Item compendiums (system packs first, index read with `fields: ['type']`), embeds it without `_id` and then removes the one item it replaces (other items of that type, such as a second kit, stay); with no match it embeds a `{name, type}` item flagged `chronicle-sync.chronicleMade`, filled from the campaign's own entry of that name when there is one (`GET /system-entries`, player view only): `system.description.value` gets the entry's text, details and trait list; the properties the field's `foundry_entry_fields` maps (a kit's bonuses) are written at their `system.*` paths (`entryItemValues`: `number`, `text`, or `tiers` split into `tier1`–`tier3`; a value that doesn't read is left out); and the flags record `entrySlug`, `entryUpdatedAt` and `entryFormat`. The entry's text may be Markdown (entries written through the AI tools) or HTML; `_entry-text.mjs` turns Markdown into HTML, drops `---` rules and `{@category term}` markers, and makes each `@[Page]` mention a `<a data-mention-id>` anchor when a synced journal of that name exists (drawn by `mention-links.mjs`), else plain words (`tools/test-entry-text.mjs`). On later pulls, a sync-made item whose entry's `updatedAt` changed, or whose `entryFormat` is older than `ENTRY_TEXT_FORMAT`, gets its text and mapped values rewritten (`planEntryRefresh`); a description still holding GM-only content keeps the item name-only (`_campaign-entry-item.mjs`, `tools/test-campaign-entry-item.mjs`). An entry property that is an ability (an object of named text parts, the shape of a package kit's `signature_ability`, such as a homemade kit's signature ability) becomes a Draw Steel ability item beside the made item, flagged `chronicleMade`, `entryAbility` (`field:entry name:part`) and `entryAbilityHash`: a power roll naming characteristics ("Agility or Reason") is the system's `@chr` roll over them, a tier's "3 + A or R" damage reads `3 + @chr`, the action type and a heroic cost map to the item's type and resource, and the rest of the text is read as creature abilities are. It is rebuilt when the ability changes (so a GM's edit to that item is replaced then, as with creature abilities; to keep one, add it under its own item) and removed when its made item is swapped away or the entry stops holding it; an ability the GM added under the same name wins, and only fields whose entries were read are touched (`ActorSync._applyEntryAbilities`, from both the pull and `_refreshMadeItems`; `_entry-abilities.mjs`, `tools/test-entry-abilities.mjs`). An entry edit changes no hero's page, so Chronicle announces it (`system_entry.changed {fieldKey}`, GM sockets) and `ActorSync._refreshMadeItems` re-reads that field's entries and refreshes every linked hero's sync-made item against the picks last applied (`identityApplied`); connect runs it for every field too, for edits made while the world was closed. Entries are read only when a field needs them, cached 30 seconds, and a 404 stops the reads for the session. An empty Chronicle value does nothing. The picks applied are recorded on the actor (`identityApplied`); a pick unchanged since then leaves a GM's own swap alone, and an actor with no record yet (never applied, such as one that existed before a system mapped the field) only has empty slots filled, never an item replaced; that first apply records its picks, even none, so a later Chronicle pick swaps the item. In the other direction a single-item field whose item the actor lacks is left out of a push rather than sent empty, so a Chronicle-built hero without its Foundry-led class item keeps its class, subclass and level in Chronicle (`buildChronicleFields`, `tools/test-generic-adapter.mjs`). A field that also sets `foundry_item_join` (a tactician's two kits) holds every item's name joined with ", " in a push, and in a pull each name the actor lacks replaces an item of that type Chronicle no longer names, else is added (`planJoined`). Foundry fires no actor update when an embedded item is added, edited or removed, so `ActorSync` watches `createItem`/`updateItem`/`deleteItem` for the item types a single-item field reads (`adapter.itemFieldTypes`) and joins them to the actor's debounced push as an `ITEMS_CHANGED` entry (`_actor-field-diff.mjs`); a flag-only item edit and sync's own writes are skipped. A removal leaving no item of that type sends an identity field as `""`, so Chronicle drops the pick; a removed class is still left out (`tools/test-actor-push.mjs`, bench `fdy-identity-item-push`). An item that still has the name Foundry gives a new, empty item of its type ("Complication", "New Complication") counts as absent the same way (`isPlaceholderName`), so the type's name never arrives as the hero's pick. The writes carry `chronicleSync` and `chronicleSyncApply` so no item hook pushes them back; a failure leaves the sheet as it was and shows one GM notice. `tools/test-identity-item-plan.mjs`, bench `chr-identity-items`.
- **Finish your hero (class).** Class stays Foundry-led, so a Chronicle-built hero arrives without its class item. After the identity items, the GM's sync records Chronicle's pick on the actor (`classPick` flag: `{name, level}`, the field mapped to the `class` item, else the page's `class` field) while the sheet has no class item, and clears it once one is there (`_finish-hero.mjs`, `tools/test-finish-hero.mjs`). `scripts/finish-hero.mjs` runs on every client: the player who owns the actor gets one card per session ("Finish in Foundry" / "Later"); Finish finds the class like an identity item and, on dnd5e, opens its advancement window for a new item (the class's `levels` set to Chronicle's level); on other systems it opens the sheet and hands it the class as a drop (`DragEvent` with `{type: 'Item', uuid}`), so the system runs what a dragged class runs. Every owner's sheet (the GM's too) shows a line naming the pick until a class item is on it; the player's line has the Finish button. Nothing is written by sync to the class itself. A subclass works the same way once the class is on the sheet: names Chronicle's subclass field holds (a conduit's two domains, joined with ", ") that no subclass item matches are noted as `subclassPick`; the owner (GM included) gets one card per pick and a sheet line with an Add button that hands the subclass to the sheet as a drop. The note clears on the next pull once the items are there (`subclassPicks`, `subclassesToFinish`, bench `chr-class-pick`).
- **Transformation layers (Chronicle → Foundry).** Each layer Chronicle has on a linked hero (`GET /entities/:id/layers`, re-read on `hero_layers.changed` and at connect for the heroes the change feed lists under `hero_layers`) becomes one Active Effect on the actor, named after the layer, flagged `chronicle-sync.layer` with the layer, a fingerprint and the field keys it changes. `_layer-effects.mjs` (pure) plans creates, updates and deletes: a `set`/`add` on a field whose `foundry_path` starts `system.` is an override/add (an object set is one override per member, `"@level"` is the hero's level), the rest goes in the description; only flagged effects are touched; an unchanged layer writes nothing, and a rewrite keeps the GM's on/off choice. A Chronicle copy re-plans from the stored layers with no read, so `"@level"` follows the hero. Fields a layer effect changes are left out of pushes (`_withoutLayered`), so a layer never lands in the hero's own fields. A 403 `addon_disabled` or 404 stops the reads until the next message. Writes carry `chronicleSync` and `chronicleSyncApply`. `tools/test-layer-effects.mjs`, bench `chr-layer-effect`, `chr-layer-offline`.
- **Actor pushes** are debounced per actor, take the mapped fields the edit touched (`_actor-field-diff.mjs`, adapter `toChronicleFieldsChanged`) and lay them over the entity's current `fields_data` before the PUT (`_putFieldsMerged`), because older Chronicle replaces the whole set on that route; a failed read pushes nothing. The name goes first with the stored version, then re-read `updated_at` after the fields PUT. `tools/test-actor-push.mjs`.

Protocol: API-CONTRACT.md. Handled: `entity.*`/`entity_type.*` → JournalSync;
`marker.*`, `map.*`, `drawing.*`, `token.*`, `layer.*`, `fog.*` → MapSync;
`calendar.event.*`, `calendar.date.advanced` (plus the display-only types
above) → CalendarSync; `relation.*` → ItemSync; `stash.*`, `downtime.changed` →

`negotiation-mirror.mjs` and creature sync; `quest.updated`,
`notice_boards.updated` → `quest-board.mjs` (refetch only); `cutscene.foundry`,
`cutscene.foundry_stop` → `cutscenes.mjs`; `sync.status` →

A "Stashes" title-bar button on a Chronicle-linked character sheet (players on
characters they own in Foundry, the GM on all) opens the Stashes window. Hidden
when Chronicle has no stash routes or the Armory addon is off (404 on the probe).

- **Relay.** Only the GM client holds the API key. A player's window emits `stash:request` on `module.chronicle-sync`; only the active GM (`game.users.activeGM`) answers. The member acted for is `userMappings` looked up by the **sender id Foundry passes as the socket listener's second argument**, never a payload field. No mapping, a character the sender does not own, or no active GM each give a clear message. Socket traffic may reach every client, so each reply is encrypted to the asking window (`_stash-crypto.mjs`); `recipients` is a best-effort extra. Replies/notices are honoured only from a GM sender. `stash:refresh` is a bare hint with no ids, so hidden characters' ids never reach players.
- **Request cards.** A message counts as a card only if a GM wrote it (players can create messages with the same markup); the move id is read from the message flag, never the markup. Each pending request gets one whispered chat card with Approve / Turn down, deduplicated on startup/reconnect (`onInitialSync` fetches `GET /stashes/requests`) and rewritten on `stash.settled` or a local press.
- **Refresh.** `stash.moved` / `stash.money_changed` re-pull the touched linked actors: `ActorSync.refreshFromChronicle`, then `ItemSync.refreshInventory` (the same reconcile as a `relation.*` message; never deletes on its own). The one removal: after an APPLIED item move away from a character, the Foundry item linked to the moved item entity whose relation is gone, counting its `unlinkedRelationId` if the move's relation event unlinked it first (`_stash-reconcile.mjs`). Events carry no item id, so they never delete.
- **Live window.** `downtime.changed` and refresh notices reach open windows through the `chronicleStashChanged` hook, relayed to players over the socket.
- **Limits.** A second GM's window calls the API from its own client and needs its own API setup. "Character actor" is approximated as "carries a Chronicle `entityId` flag". Sender identity relies on Foundry passing the sender user id as the listener's second argument.

## Security posture

Chronicle Sync trusts one operator-configured Chronicle deployment, with
**targeted sanitization at the highest-risk surfaces**: stored HTML, `<img src>`
URLs, DOM interpolation of Chronicle data. Response field shapes and WS payload
contents beyond the `type` allowlist are not validated.

### Auth surfaces: never cross

| Surface | Auth carrier | URL shape | Audience |
|---|---|---|---|
| REST (sync) | `Authorization: Bearer ${apiKey}` | `${apiUrl}/api/v1/campaigns/${campaignId}/...` | All sync modules, dashboard, wizard |
| WebSocket (sync) | `?token=${apiKey}` | `wss://<apiUrl host>/ws?token=...&client=foundry-module` | `api-client.mjs::_doConnect` only |
| Module manifest / zip | Install-URL signed token | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.json\|module.zip?token=...` | Foundry's update check and installer |
| Notebook and calendar frames | The player's notes grant (`cnt_…`) handed to the frame by `postMessage` at Chronicle's origin; kept in client setting `notesGrants` keyed by Foundry user | `${apiUrl}/embed/campaigns/${campaignId}/notes/...` (the frame calls `/api/notes-app/...`) | `player-notebook.mjs` only; never the GM's `apiKey` |

The install-URL token is Chronicle-signed with campaign+expiry claims `/api/v1/`
rejects; `apiKey` is a bearer token `module.json` rejects. Never consolidate
them. Pinned by `tools/test-api-client-security.mjs`.

### Shared rolls

A `gm` or `blind` Chronicle roll is only ever posted as a whisper to GM users
(plus the linked roller for `gm`), never as a public message, so Foundry does
not deliver it to other players. A Foundry message is sent to Chronicle only
when it is public, blind, or whispered to at least one GM; a self roll or a
whisper to players alone stays in Foundry.

### Trust posture

Each row is a footgun if unvalidated: a tampered Chronicle response could reach
a player's browser as XSS, a redirect-and-leak, a URL break-out or a leaked
bearer token.

| Class | What we trust | What we validate | Where | Pin |
|---|---|---|---|---|
| HTML for `JournalEntry.text.content` | Chronicle's bluemonday UGCPolicy at write | Pre-sanitize via Foundry's `cleanHTML` (`foundry.utils` on v14, `TextEditor` before) at ingress | `_html-sanitizer.mjs` | `test-html-sanitizer.mjs` |
| Pictures inside page text | Chronicle's media path | Only `/media/<uuid>` (UUID-checked) is copied; signed link on the `apiUrl` host; raster MIME, declared and served types match; GM-only pictures never copied | `picture-store.mjs`, `_inline-pictures.mjs` | `test-inline-pictures.mjs` |
| Image URLs from map sub-resources | Operator-configured `apiUrl` host | `_isAllowedImageHost` rejects a full-URL `image_url`/token `image` whose host differs from `apiUrl` (map, picture, avatar and shop-room code); rejection → blank `<img>` + warning | `_url-validation.mjs` | `test-url-validation.mjs` |
| Connection-test results | Nothing | `createTextNode`, never `innerHTML` of Chronicle data | `chronicle-settings.mjs::stepItem` | `test-sync-dashboard-xss.mjs` |
| Sync history rows | Nothing | Node descriptions; `toDom` sets only text and attributes | `_history-view.mjs::toDom` | `test-history-view.mjs` |
| `campaignId` setting | Operator typed it correctly | UUID shape enforced before URL interpolation (`fetch`/`uploadMedia`): `describeCampaignIdError`, called through `_validateCampaignIdOrThrow` | `_settings-validation.mjs`, `api-client.mjs` | `test-campaign-id-validation.mjs` |
| Outbound error log entries | Nothing (a response body may echo the request) | `_scrubAuthHeaders` redacts `Bearer <token>` / `?token=<value>` before storing | `api-client.mjs` | `test-api-client-secrets.mjs` |

**Sanitization layers on Chronicle HTML:** (1) server-side bluemonday UGCPolicy
on write; (2) Foundry ingress: `_sanitizeIncomingHTML` wraps `cleanHTML`, every
pulled page goes through `JournalSync._pullHtml`, and `gm-secret-view.mjs`
sanitizes the GM-only content it shows (operator escape:
`skipIncomingSanitization`, default off); (3) render-time
`TextEditor.enrichHTML`. `tools/test-html-sanitizer.mjs` statically scans every
ingestion site.

**Descriptor integrity:** CI (`tools/check-package-descriptor.mjs`) and runtime
(`module.mjs::_runtimeValidateDescriptor`, GM-gated `ready` hook, non-fatal
`ui.notifications.error` on drift) share `validateDescriptor`.

**API key:** a Foundry **client** setting (CLAUDE.md), hidden from Foundry's
list and entered in a password field. Server side it is rate-limited (300
req/min default, per key), campaign-scoped, with an optional device-fingerprint
lock. See Chronicle's `.ai/conventions.md` security section and tenets T-B1,
T-B4 in CLAUDE.md.

**Module version header:** REST requests (`fetch`, `uploadMedia`) send
`X-Chronicle-Module-Version` (`_module-version.mjs`); omitted if unreadable;
caller headers win. An older Chronicle's CORS refuses it, so a network
TypeError on a request that carried it retries once without and drops it for
the session. The dashboard's raw probes never send it.
`tools/test-module-version-header.mjs`.

**Connect line:** the client setting `connectLine` takes
`chronicle://…/c/<campaignId>?key=…` (`chronicle+http://` for plain http),
parsed by `_connect-line.mjs`. `applyConnectLine` (`settings.mjs`, GM only)
writes `apiUrl`, `campaignId` and the client `apiKey`, then clears the line;
nothing changes on an invalid line. Saving a changed connection calls
`SyncManager.applyConnection()` (`_connection-change.mjs`): a sync that never
started starts, the same campaign reconnects the socket (the client reads the
address and key on each connect), and only a different campaign asks the GM to
reload, since every part holds state for the old one. `start()` runs its body
once; a start that stopped early can run again. The Settings window then runs
Test connection by itself. Format: API-CONTRACT.md → "Connect Line".
`tools/test-connect-line.mjs`, `tools/test-connection-change.mjs`.

**Status dot:** the sidebar indicator's label and tooltip come from
`CHRONICLE.Status.*` through `_status-dot.mjs`; while connected the tooltip
says when Chronicle last sent a change, worked out again on hover. A
deliberate disconnect (`api.wantsConnection` false) raises no "Connection
lost" toast. `tools/test-status-dot.mjs`.

**Conflict notices:** "Chronicle wins" and "Foundry wins" toast with
`CHRONICLE.Notifications.ConflictKept*` and log to History; "Newest wins"
only logs to History, since it is the GM's rule working as chosen. The first
sync's success goes to History without a toast.

## Field naming

API-CONTRACT.md has the canonical names. Relations are asymmetric on purpose:
reads and WS are camelCase (`sourceEntityId`, `targetEntityId`, `relationType`;
`item-sync.mjs`, `shop-room-window.mjs`), writes are snake_case
(`target_entity_id`, `relation_type`, `reverse_relation_type`); routes are flat
(`/relations/:relationId`).

## Known limitations

- Map drawings/tokens/fog/layers are read-only SVG overlays in `MapViewerSheet`; only markers are bidirectional.
- The built-in calendar shows Chronicle's date, world state and events but is not Foundry's world clock. Players see events for the current month and one either side.
- Shop rooms: arranging stays on the Chronicle shop page. A player who joins after the GM showed a shop sees it the next time. Players buy only while the GM is in the game and showing that shop, and only once the GM has matched their Foundry user to a member. Other players' open rooms update stock when the GM's room next refreshes, which also clears a basket in progress. With two GMs, buying works only when the active GM is showing the shop. Full sync runs only for GM users.
- Crafting: the Crafting tab works only while a GM is in the game, and only once the GM has matched the player's Foundry user to a member. The bench, recipe and drop-list editors and the Director's tray stay on Chronicle. The spoils prompt holds a staged encounter's defeated only on the scene they fell on, and only until a later combat of that encounter ends; if none does, nothing drops and they can be put in by hand on Chronicle.
- PF2e character sync: only HP and name sync back (the rest derives from items/rules).
- Character sync for any system, dnd5e and pf2e included, goes through the one generic adapter and needs `foundry_path` annotations on the preset's character fields, else the adapter returns null. System matching is API-driven via each installed system's `foundry_system_id`.
- Conflicts: `ConflictError` (409, stale `expected_updated_at`) resolves per `conflictResolution`: `chronicle` (re-pull), `foundry` (force push), `newest` (the time of the unsent Foundry edit against Chronicle's `updated_at`; Chronicle wins when the edit's time is unknown). Each settled conflict, on a page or a hero's rename, also goes to Chronicle's sync history as one `status: "conflict"` row saying which side was kept and why, with field names only (`conflictEvent`). `tools/test-journal-conflict.mjs`, `tools/test-history-report.mjs`.
- Requests give up after 30 seconds (two minutes for picture uploads and downloads) so a stalled server cannot hold a sync queue open. A connect catch-up that failed is tried again after 30 seconds, one minute and two minutes while the connection stays up, and only one catch-up runs at a time (`tools/test-sync-pass.mjs`).

Tests: `tools/test-permission-sync.mjs`, `test-build-ownership.mjs`, `test-pc-claiming.mjs`.

## Install & Updates

Foundry installs and updates this module from **Chronicle**, not GitHub: the
`foundry_vtt` sub-plugin serves each campaign a signed install URL for whichever
version the owner's update choice gives (automatic, ask first, or pinned).
Chronicle pulls each version from this repo's **GitHub releases** (or GitHub's
source zip if a release has no asset); nothing is uploaded to Chronicle by hand.

**Install flow:** the owner copies the install URL from Manage → Foundry →
Chronicle issues a signed manifest URL
(`/api/v1/campaigns/{id}/foundry-vtt/module.json?token={signed}`) → pasted into
Foundry's Install Module dialog → Foundry GETs it (`manifest`/`download`
rewritten to Chronicle URLs), follows `download`, installs, and reuses that
manifest URL for every update check.

**`chronicle-package.json`** is the serving descriptor Chronicle's
`PostInstallHook` reads from the release zip: manifest location
(`package.moduleJsonPath`), fields to rewrite (`serving.rewriteFields`:
`manifest`, `download`), URL shape, whether signed tokens are required. Absent
or invalid → Chronicle falls back to hardcoded defaults. CI validates it on
every push/PR; bumping `module.json#/id` requires updating
`chronicle-package.json#/package/id` in the same commit (CI-enforced). Contract:
API-CONTRACT.md → "Chronicle-served Module Distribution".

The on-disk `module.json` `manifest`/`download` deliberately still point at
GitHub (a directly obtained zip still works and `PackagesPlugin` can auto-pull
releases); `serving.rewriteFields` rewrites them at serve time. Don't "fix" them.

**Update Source dialog** (`scripts/update-info.mjs`; Game Settings → Module
Settings → Chronicle Sync → Update Source): shows the install-time manifest URL,
classifies it (chronicle/github/unknown) with the regex
`/api/v1/campaigns/.../foundry-vtt/module.json`, and has a "Check Chronicle for
updates" button. Keep it and `chronicle-package.json` in sync if the URL shape
changes. A GM-only startup probe (`surfaceManifestRecoveryIfNeeded()` in the
`ready` hook) re-checks the URL once per session; an `auth` result shows a
sticky `ui.notifications.error` telling the GM to reinstall; other outcomes
stay silent.

**Error classification** (`update-info.mjs`), in order: Chronicle's
`body.category` when it is one of `auth | config | not_found | validation |
internal`; else HTTP status (401/403 → auth, 404 → not_found, 5xx/else →
internal); else Foundry-only `network` (fetch threw) / `parse` (bad JSON or
missing `version`). There is no local code-to-category table.

| Category | Triggered by | Icon | Hue |
|---|---|---|---|
| `auth` | `invalid_token`, 401/403 w/o body | `fa-key` | red |
| `config` | `no_package_registered`, `pinned_version_not_installed`, `token_not_initialized`, `no_version_available` | `fa-gear` | amber |
| `not_found` | `campaign_not_found`, 404 w/o body, no install-time URL recorded | `fa-magnifying-glass` | amber |
| `validation` | `descriptor_invalid` | `fa-triangle-exclamation` | amber |
| `internal` | `module_json_missing`, `ErrInternal`, 5xx w/o body | `fa-server` | red |
| `network` | fetch threw (DNS/TLS/CORS/firewall) | `fa-plug-circle-xmark` | slate |
| `parse` | bad JSON, 200 OK missing `version` | `fa-file-circle-question` | slate |

Category names are snake_case on the wire and in CSS classes (`result-auth`,
`result-not_found`). Codes: API-CONTRACT.md → "Error code catalog".

**Token rotation:** old token returns `403 invalid_token/auth` at once. No
in-place repair: uninstall and reinstall via a fresh install URL. The version
pin survives rotation.

**Releases:** Actions → Release → Run workflow with the version (X.Y.Z).
`.github/workflows/release.yml` tags main and publishes the release with
generated notes and no attachments. Chronicle installs the source zip on Check
now (Admin → Packages) and its install hook writes the tag into `module.json`,
so the `version` on main is never read.

## Foundry conventions and footguns

- **ApplicationV2 `actions` delegates only `click`.** Wire other events in `_onRender` with `addEventListener`; adding them to `actions` is silently dropped.
- **Test bootstrap.** Importing `calendar-sync.mjs` (or anything pulling `settings.mjs` → `update-info.mjs`) in a unit test throws `ReferenceError: foundry is not defined`; stub `globalThis.foundry/game/Hooks` before the dynamic `import()`. Canonical stub: `tools/test-calendar-sync-visibility.mjs`.
- **i18n key collisions are silent.** Two `registerMenu` calls can't share an i18n key (Foundry returns the first match), and a menu's keys can't reuse a setting's namespace. Menus use `CHRONICLE.SettingsWindow.Menu*` and `CHRONICLE.Settings.UpdateInfo.*`.
- **Handlebars helpers need explicit registration** in `module.mjs`'s `init` (`eq`, `neq`, `lt`, `json`, `timeAgo`); register new ones there.
- **PARTS templates need exactly one root element.** `_parsePartHTML` rejects zero or several roots, only at `app.render()` time and depending on which `{{#if}}` branch fires. Wrap the body in one root so every branch emits one. Guard: `tools/test-template-roots.mjs` (recurses every branch).
- **`lang/en.json` can't mix a dotted-flat key with a sibling literal-key string.** `expandObject` throws when both `parent.X = "..."` and `parent.X.Y = "..."` exist and **rejects the whole lang file**: every `CHRONICLE.*` key then renders raw, with no lint error. Nest the option set under a sibling key (e.g. `VisibilityOption: {Visible, Hidden, Secret}`) and keep the label flat. Guard: `tools/test-lang-expand.mjs`.
- **JournalSync skips journals owned by another sync domain.** A journal with no `entityId` flag is pushed as a new page, so JournalSync skips `isCalendarNoteJournal` (our `calendarEventId` flag), `isOldNotesJournal` (`_notes-folder.mjs`) and `isMapJournal`, as `_isHandledByActorSync` does for characters. `tools/test-calendar-note-journal.mjs`.

## Architectural decisions

- **A-1 Chronicle-served distribution.** Chronicle serves release artifacts on a per-campaign signed URL, not GitHub Releases or Foundry's Package Repository: the operator pins campaigns to different versions and controls rollout from Chronicle's admin UI without public install URLs.
- **A-2 Descriptor-driven serving.** Chronicle reads `chronicle-package.json` from the release zip, falling back to defaults, so Chronicle stays generic and any Foundry module can register its own descriptor.
- **A-3 Foundry stores the Chronicle URL.** Foundry keeps the per-campaign manifest URL and checks it for updates, never GitHub, so the owner's version pin stays authoritative. Risk: Foundry's Package Repository also lists this module under its GitHub URL and may prompt to switch (README "Updating").
- **A-4 Update Source is a manual check.** It is a diagnostic, not part of the update loop: Foundry's Update All is the production path, and auto-correcting a deliberately GitHub-installed instance would be too aggressive.
