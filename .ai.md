# Chronicle Sync: Foundry VTT Module

Bidirectional real-time sync between Chronicle and a Foundry VTT (v12-v14)
world, over REST + WebSocket. Wire contract: API-CONTRACT.md. Tunable values:
CONSTANTS.md. Live checks: TESTING.md. Cross-cutting rules: CLAUDE.md →
"Rules the code must keep" (`_syncing` guard, real-time calendar date guard,
display-only calendar sub-resources, calendar blackout).

## Architecture

```
module.mjs (entry point)
  └─ SyncManager (sync-manager.mjs)
       ├─ ChronicleAPI (api-client.mjs)    ← REST + WebSocket client
       ├─ JournalSync (journal-sync.mjs)   ← Entity ↔ JournalEntry
       ├─ MapSync (map-sync.mjs)           ← Map + markers/drawings/tokens/fog/layers ↔ JournalEntry (image page) with overlay
       ├─ CalendarSync (calendar-sync.mjs) ← Chronicle calendar date/events/world state; feeds the built-in calendar (calendar-bar.mjs)
       ├─ ShopWidget (shop-widget.mjs)     ← Chronicle shops as shop rooms in Foundry
       ├─ ItemSync (item-sync.mjs)         ← Actor inventory ↔ Chronicle relations
       ├─ SyncDashboard (sync-dashboard.mjs) ← ApplicationV2 window: Overview, Linked, Problems, Settings
       ├─ ActorSync (actor-sync.mjs)       ← Character entity ↔ Actor
       │    └─ generic-adapter.mjs         ← API-driven adapter (all systems)
       └─ CreatureSync (creature-sync.mjs) ← Creature page → NPC actor (Stamina/conditions back, if allowed)
```

Data flow: GM's `ready` → `SyncManager.start()` validates config, initializes
modules, connects the WebSocket → initial sync (mappings since `lastSyncTime`,
then the change feed) → live: WS messages route to modules, Foundry hooks push
local changes over REST.

`scripts/_realtime-date-guard.mjs` guards `CalendarSync.pushDate`; its GM notice
is a module-level singleton, once per session.

### Applied-date confirmation

Chronicle's sync chip distinguishes what Foundry *saw* (the `GET /calendar/date`
beacon) from what it *applied*. `confirmAppliedDate(api, {year, month, day})` in
`_applied-date-confirm.mjs` posts `POST /calendar/date/confirm` only after a real
apply; 404/405 (older Chronicle) is tolerated and logged once per session. No
Foundry calendar is integrated, so nothing calls it yet (TODO(#95)).
`_calendar-sync-state.mjs` (`classifyCalendarSyncState`: paused > structure
mismatch > date drift > in-sync, fails open) is likewise unused until then.

### Sync wire rules

- `_onSyncStatus` reads `msg.status ?? msg.payload?.status` (emit shapes vary).
- Visibility toggles: `POST /entities/:id/reveal`, not a bare `PUT` (400s without a name).
- Item relations: flat `DELETE|PUT /relations/:relationId`, snake_case bodies.
- Calendar events: `isChronicleEventPublic` decides whether a player may see an event (GM-only events, and `everyone` events with `visibility_rules`, may not); fails closed; the players' snapshot keeps only events it passes.

Pinned by `tools/test-sync-wire-fix.mjs`, `test-calendar-sync-state.mjs`, `test-calendar-sync-visibility.mjs`.

### Journals, catch-up and concurrency

- **Journal made in Foundry → Chronicle page.** `POST /entities` with a real `entity_type_id` (world setting `journalCreateTypeId`; unset means the campaign's first non-character type), then the text as `entry` in `PUT /entities/:id`, because the create request has no text field. Journals owned by MapSync (`mapId` page flag or the Maps folder), linked to a calendar event (`calendarEventId` flag) or in the old Chronicle Notes folder are skipped. `_journal-create.mjs`, `_journal-ownership.mjs`.
- **Per-document guarding, no global flag.** Incoming changes apply per entity id in arrival order (`_keyed-queue.mjs`); creates re-check for an existing journal inside the queue slot. Every write sync makes passes `syncOptions()` (a fresh `{chronicleSync: true}` per write, since Foundry 14 writes into the options it gets), and the create/update/delete hooks ignore only writes carrying it, so a GM edit during an apply still pushes. A journal whose create POST is in flight is remembered so the `entity.created` broadcast makes no second copy.
- **Unsent local edit wins.** An incoming change for a journal with a debounced push pending is not applied; the stored `chronicleUpdatedAt` moves to the incoming version, the push goes out (updates are partial) and the GM gets a warning.
- **Catch-up on connect.** `/sync/pull` is walked through `has_more` in 1000-row pages, each resuming just before the previous page's last `updated_at` (`since` is strict, no cursor), repeats dropped by id (`_sync-pull-walk.mjs`). `lastSyncTime` is the first page's `server_time`, written only after the whole walk; `_initialSyncDone` latches only on success. `JournalSync.onInitialSync` resyncs the entity list (changed pages plus pages created since the last sync; an older page with no journal was deleted or never imported and is not recreated; a first connect creates nothing), then sets aside journals whose page returns 404, only after a complete walk. Actor lists page via `walkEntityPages`.
- **Change feed.** Before modules apply, `SyncManager` reads `GET /sync/changes` from the saved `changeFeedCursor` (`{campaignId, seq, areas, createdAfter, types}`), at least 2.5 s after the socket opened (Chronicle holds back its newest 2 s). A module with `feedArea` gets `{feed: {mode: 'delta', changes}}` when the cursor was saved while its area was syncing, else `{mode: 'full'}` (no cursor, another campaign's, `resetRequired`, or the area was off). A module with `feedType` also gets `full` unless the cursor's `types` include it. The cursor is saved only when every feed area applied cleanly; replays are harmless. No feed (older Chronicle, a player's key) means a full rescan and no cursor. `_change-feed.mjs`, `tools/test-change-feed.mjs`. Per module:
  - `ItemSync` (`feedType: 'relation'`) reconciles each listed character's whole inventory from `GET /entities/:id/relations`: add, adopt a Foundry item whose push has not recorded its relation yet, update quantity/equipped, unlink (never delete) items whose relation is not on that character; nothing written when it already matches; serialized per actor. A new Foundry item arriving with a relation flag is a copy: it drops the flag and is pushed as its own relation. Live `relation.*` messages do the same (`_inventory-plan.mjs`).
  - `MapSync` (`feedType: 'marker'`) still reads `GET /maps` (no feed row for a map) and refreshes the items of each map the feed names: fog by map id; markers, drawings, tokens and layers by finding the item among the GM cache and stored page flags, every map once when one cannot be placed. A full catch-up refreshes no items (`_map-feed.mjs`).
  - `ActorSync` refetches only listed characters that have a linked actor, skips actors at their version, unlinks (keeps) the actor of a removed character, never creates actors at connect, ignores a copy older than the actor's recorded version, and after a feed catch-up counts unlinked actors locally instead of listing Chronicle.
  - `JournalSync` refetches only the listed pages: skip at the recorded version, create only for a page whose `created_at` is after the cursor's `createdAfter` (it moves only with the cursor; a walk cut short keeps the old one), set aside on `deleted` or a 404 after the usual checks.
- **Versions only move forward.** `chronicleUpdatedAt` is never set older than it is: an incoming older copy is ignored (an echo built before a later save); equal versions still apply (one-second precision). A permissions push identical to the last one sent (`pushedPermissions`) is skipped; after a real one the module reads the page back for the stamped version, because Chronicle's permissions save returns none and broadcasts the old one. `tools/test-journal-versions.mjs`.
- **Journal pushes** come from journal edits and page create/edit/delete hooks (page text never fires `updateJournalEntry`), through the same per-journal debounce. A pulled sync mapping never creates a journal: a mapping without one means the GM deleted it here; the dashboard Resync brings it back on purpose.
- **Claim ownership (Chronicle → Foundry).** When a linked character's `owner_user_id` is applied (live update, create, or the connect/full-resync pass over cached `chronicleOwnerUserId` flags), the GM's client gives the mapped Foundry user (`userMappings`) OWNER on the actor, inside `ActorSync._applyClaimOwnership` under `_syncing`; the write carries `chronicleSync` and `chronicleSyncApply`. Connect auto-matches a member to a Foundry user only when the name is unique among both. `_claim-ownership-plan.mjs` returns `{grantUserId, staleOwnerUserIds, unmapped}`. Ownership is only ever added: on a hand-over A to B, B gets OWNER, A keeps theirs and the GM gets one notice; unclaiming changes nothing; an owner with no live Foundry user changes nothing, gives one GM notice per session and shows in Settings → Players as a claimant with no Foundry user. A user who already has OWNER (or a GM) is skipped. Foundry → Chronicle ownership is sent only when the actor is first created (`_resolveOwnerUserId`).
- **Identity items (Chronicle → Foundry).** A pulled character whose `ancestry`, `culture`, `career` or `kit` differs from the actor's first embedded item of that type gets that item swapped, GM client only, inside `ActorSync._updateActorFromEntity` / `_onCharacterCreated` under `_syncing`. Eligible fields have `foundry_collection` + `foundry_item_single` and one `foundry_item_type` that is not class/subclass, and a key other than `level`/`heroic_resource_name` (Foundry-led). `_identity-item-plan.mjs` decides swaps; `_identity-item-apply.mjs` finds an Item of that type and name (case-insensitive) in `game.items`, then Item compendiums (system packs first, index read with `fields: ['type']`), embeds it without `_id`, then removes the one it replaces (other items of that type stay). With no match it embeds a `{name, type}` item flagged `chronicle-sync.chronicleMade`, filled from the campaign's entry of that name when there is one (`GET /system-entries`, player view only): description gets the entry's text, details and trait list; flags record `entrySlug` and `entryUpdatedAt`. Later pulls rewrite a sync-made item whose entry's `updatedAt` changed (`planEntryRefresh`); a description still holding GM-only content keeps the item name-only (`_campaign-entry-item.mjs`). Entries are read only when a field needs them, cached 30 s, and a 404 stops reads for the session. An empty Chronicle value does nothing; the Chronicle value wins, so an item swapped in Foundry is swapped back on the next pull. Writes carry `chronicleSync` and `chronicleSyncApply`; a failure leaves the sheet as it was and shows one GM notice.
- **Actor pushes** are debounced per actor, take the mapped fields the edit touched (`_actor-field-diff.mjs`, adapter `toChronicleFieldsChanged`) and lay them over the entity's current `fields_data` before the PUT (`_putFieldsMerged`), because older Chronicle replaces the whole set on that route; a failed read pushes nothing. The name goes first with the stored version, then `updated_at` is re-read after the fields PUT.

## Stashes

A "Stashes" title-bar button on a Chronicle-linked character sheet (players on
characters they own in Foundry, the GM on all) opens the Stashes window. Hidden
when Chronicle has no stash routes or the Armory addon is off (404 on the probe).

- **Relay.** Only the GM client holds the API key. A player's window emits `stash:request` on `module.chronicle-sync`; only the active GM (`game.users.activeGM`) answers. The member acted for is `userMappings` looked up by the **sender id Foundry passes as the socket listener's second argument**, never a payload field. No mapping, a character the sender does not own, or no active GM each give a clear message. Socket traffic may reach every client, so each reply is encrypted to the asking window (`_stash-crypto.mjs`); `recipients` is a best-effort extra. Replies/notices are honoured only from a GM sender. `stash:refresh` is a bare hint with no ids, so hidden characters' ids never reach players.
- **Request cards.** A message counts as a card only if a GM wrote it (players can create messages with the same markup); the move id is read from the message flag, never the markup. Each pending request gets one whispered chat card with Approve / Turn down, deduplicated on startup/reconnect (`onInitialSync` fetches `GET /stashes/requests`) and rewritten on `stash.settled` or a local press.
- **Refresh.** `stash.moved` / `stash.money_changed` re-pull the touched linked actors: `ActorSync.refreshFromChronicle`, then `ItemSync.refreshInventory` (the same reconcile as a `relation.*` message; never deletes on its own). The one removal: after an APPLIED item move away from a character, the Foundry item linked to the moved item entity whose relation is gone, counting its `unlinkedRelationId` if the move's relation event unlinked it first (`_stash-reconcile.mjs`). Events carry no item id, so they never delete.
- **Live window.** `downtime.changed` and refresh notices reach open windows through the `chronicleStashChanged` hook, relayed to players over the socket.
- **Limits.** A second GM's window calls the API from its own client and needs its own API setup. "Character actor" is approximated as "carries a Chronicle `entityId` flag". Sender identity relies on Foundry passing the sender user id as the listener's second argument.

## Security posture

Chronicle Sync trusts one operator-configured Chronicle deployment, with
**targeted sanitization at the highest-risk surfaces**: stored HTML, `<img src>`
URLs, DOM interpolation of Chronicle data. Response field shapes and WS payload
contents beyond the `type` allowlist are not validated.

### Auth surfaces: never cross

| Surface | Auth carrier | URL shape | Audience |
|---|---|---|---|
| REST (sync) | `Authorization: Bearer ${apiKey}` | `${apiUrl}/api/v1/campaigns/${campaignId}/...` | All sync modules, dashboard, wizard |
| WebSocket (sync) | `?token=${apiKey}` | `wss://<apiUrl host>/ws?token=...&client=foundry-module` | `api-client.mjs::_doConnect` only |
| Module manifest / zip | Install-URL signed token | `${apiUrl}/api/v1/campaigns/${campaignId}/foundry-vtt/module.json\|module.zip?token=...` | Foundry's update check and installer |
| Notebook and calendar frames | The player's notes grant (`cnt_…`) handed to the frame by `postMessage` at Chronicle's origin; kept in client setting `notesGrants` keyed by Foundry user | `${apiUrl}/embed/campaigns/${campaignId}/notes/...` (the frame calls `/api/notes-app/...`) | `player-notebook.mjs` only; never the GM's `apiKey` |

The install-URL token is Chronicle-signed with campaign+expiry claims `/api/v1/`
rejects; `apiKey` is a bearer token `module.json` rejects. Never consolidate
them. Pinned by `tools/test-api-client-security.mjs`.

### Trust posture

Each row is a footgun if unvalidated: a tampered Chronicle response could reach
a player's browser as XSS, a redirect-and-leak, a URL break-out or a leaked
bearer token.

| Class | What we trust | What we validate | Where | Pin |
|---|---|---|---|---|
| HTML for `JournalEntry.text.content` | Chronicle's bluemonday UGCPolicy at write | Pre-sanitize via Foundry's `cleanHTML` (`foundry.utils` on v14, `TextEditor` before) at ingress | `_html-sanitizer.mjs` | `test-html-sanitizer.mjs` |
| Pictures inside page text | Chronicle's media path | Only `/media/<uuid>` (UUID-checked) is copied; signed link on the `apiUrl` host; raster MIME, declared and served types match; GM-only pictures never copied | `picture-store.mjs`, `_inline-pictures.mjs` | `test-inline-pictures.mjs` |
| Image URLs from map sub-resources | Operator-configured `apiUrl` host | `_isAllowedImageHost` rejects a full-URL `image_url`/token `image` whose host differs from `apiUrl` (map, picture, avatar and shop-room code); rejection → blank `<img>` + warning | `_url-validation.mjs` | `test-url-validation.mjs` |
| Connection-test results | Nothing | `createTextNode`, never `innerHTML` of Chronicle data | `chronicle-settings.mjs::stepItem` | `test-sync-dashboard-xss.mjs` |
| Sync history rows | Nothing | Node descriptions; `toDom` sets only text and attributes | `_history-view.mjs::toDom` | `test-history-view.mjs` |
| `campaignId` setting | Operator typed it correctly | UUID shape enforced before URL interpolation (`fetch`/`uploadMedia`): `describeCampaignIdError`, called through `_validateCampaignIdOrThrow` | `_settings-validation.mjs`, `api-client.mjs` | `test-campaign-id-validation.mjs` |
| Outbound error log entries | Nothing (a response body may echo the request) | `_scrubAuthHeaders` redacts `Bearer <token>` / `?token=<value>` before storing | `api-client.mjs` | `test-api-client-secrets.mjs` |

**Sanitization layers on Chronicle HTML:** (1) server-side bluemonday UGCPolicy
on write; (2) Foundry ingress: `_sanitizeIncomingHTML` wraps `cleanHTML`, every
pulled page goes through `JournalSync._pullHtml`, and `gm-secret-view.mjs`
sanitizes the GM-only content it shows (operator escape:
`skipIncomingSanitization`, default off); (3) render-time
`TextEditor.enrichHTML`. `tools/test-html-sanitizer.mjs` statically scans every
ingestion site.

**Descriptor integrity:** CI (`tools/check-package-descriptor.mjs`) and runtime
(`module.mjs::_runtimeValidateDescriptor`, GM-gated `ready` hook, non-fatal
`ui.notifications.error` on drift) share `validateDescriptor`.

**API key:** a Foundry **client** setting (CLAUDE.md), hidden from Foundry's
list and entered in a password field. Server side it is rate-limited (300
req/min default, per key), campaign-scoped, with an optional device-fingerprint
lock. See Chronicle's `.ai/conventions.md` security section and tenets T-B1,
T-B4 in CLAUDE.md.

**Module version header:** REST requests (`fetch`, `uploadMedia`) send
`X-Chronicle-Module-Version` (`_module-version.mjs`); omitted if unreadable;
caller headers win. An older Chronicle's CORS refuses it, so a network
TypeError on a request that carried it retries once without and drops it for
the session. The dashboard's raw probes never send it.
`tools/test-module-version-header.mjs`.

**Connect line:** the client setting `connectLine` takes
`chronicle://…/c/<campaignId>?key=…` (`chronicle+http://` for plain http),
parsed by `_connect-line.mjs`. `applyConnectLine` (`settings.mjs`, GM only)
writes `apiUrl`, `campaignId` and the client `apiKey`, then clears the line;
nothing changes on an invalid line. `SyncManager` reads settings in `start()`
and is not restarted, so the GM reloads. Format: API-CONTRACT.md → "Connect
Line". `tools/test-connect-line.mjs`.

## Field naming

API-CONTRACT.md has the canonical names. Relations are asymmetric on purpose:
reads and WS are camelCase (`sourceEntityId`, `targetEntityId`, `relationType`;
`item-sync.mjs`, `shop-room-window.mjs`), writes are snake_case
(`target_entity_id`, `relation_type`, `reverse_relation_type`); routes are flat
(`/relations/:relationId`).

## Known limitations

- Map drawings/tokens/fog/layers are read-only SVG overlays in `MapViewerSheet`; only markers are bidirectional.
- The built-in calendar shows Chronicle's date, world state and events but is not Foundry's world clock. Players see events for the current month and one either side.
- Shop rooms: arranging stays on the Chronicle shop page. A player who joins after the GM showed a shop sees it the next time. Players buy only while the GM is in the game and showing that shop, and only once the GM has matched their Foundry user to a member. Other players' open rooms update stock when the GM's room next refreshes, which also clears a basket in progress. With two GMs, buying works only when the active GM is showing the shop. Full sync runs only for GM users.
- PF2e character sync: only HP and name sync back (the rest derives from items/rules).
- Character sync for any system, dnd5e and pf2e included, goes through the one generic adapter and needs `foundry_path` annotations on the preset's character fields, else the adapter returns null. System matching is API-driven via each installed system's `foundry_system_id`.
- Conflicts: `ConflictError` (409, stale `expected_updated_at`) resolves per `conflictResolution`: `chronicle` (re-pull), `foundry` (force push), `newest` (compare timestamps).

Tests: `tools/test-permission-sync.mjs`, `test-build-ownership.mjs`, `test-pc-claiming.mjs`.

## Install & Updates

Foundry installs and updates this module from **Chronicle**, not GitHub: the
`foundry_vtt` sub-plugin serves each campaign a signed install URL for whichever
version the owner's update choice gives (automatic, ask first, or pinned).
Chronicle pulls each version from this repo's **GitHub releases** (or GitHub's
source zip if a release has no asset); nothing is uploaded to Chronicle by hand.

**Install flow:** the owner copies the install URL from Manage → Foundry →
Chronicle issues a signed manifest URL
(`/api/v1/campaigns/{id}/foundry-vtt/module.json?token={signed}`) → pasted into
Foundry's Install Module dialog → Foundry GETs it (`manifest`/`download`
rewritten to Chronicle URLs), follows `download`, installs, and reuses that
manifest URL for every update check.

**`chronicle-package.json`** is the serving descriptor Chronicle's
`PostInstallHook` reads from the release zip: manifest location
(`package.moduleJsonPath`), fields to rewrite (`serving.rewriteFields`:
`manifest`, `download`), URL shape, whether signed tokens are required. Absent
or invalid → Chronicle falls back to hardcoded defaults. CI validates it on
every push/PR; bumping `module.json#/id` requires updating
`chronicle-package.json#/package/id` in the same commit (CI-enforced). Contract:
API-CONTRACT.md → "Chronicle-served Module Distribution".

The on-disk `module.json` `manifest`/`download` deliberately still point at
GitHub (a directly obtained zip still works and `PackagesPlugin` can auto-pull
releases); `serving.rewriteFields` rewrites them at serve time. Don't "fix" them.

**Update Source dialog** (`scripts/update-info.mjs`; Game Settings → Module
Settings → Chronicle Sync → Update Source): shows the install-time manifest URL,
classifies it (chronicle/github/unknown) with the regex
`/api/v1/campaigns/.../foundry-vtt/module.json`, and has a "Check Chronicle for
updates" button. Keep it and `chronicle-package.json` in sync if the URL shape
changes. A GM-only startup probe (`surfaceManifestRecoveryIfNeeded()` in the
`ready` hook) re-checks the URL once per session; an `auth` result shows a
sticky `ui.notifications.error` telling the GM to reinstall; other outcomes
stay silent.

**Error classification** (`update-info.mjs`), in order: Chronicle's
`body.category` when it is one of `auth | config | not_found | validation |
internal`; else HTTP status (401/403 → auth, 404 → not_found, 5xx/else →
internal); else Foundry-only `network` (fetch threw) / `parse` (bad JSON or
missing `version`). There is no local code-to-category table.

| Category | Triggered by | Icon | Hue |
|---|---|---|---|
| `auth` | `invalid_token`, 401/403 w/o body | `fa-key` | red |
| `config` | `no_package_registered`, `pinned_version_not_installed`, `token_not_initialized`, `no_version_available` | `fa-gear` | amber |
| `not_found` | `campaign_not_found`, 404 w/o body, no install-time URL recorded | `fa-magnifying-glass` | amber |
| `validation` | `descriptor_invalid` | `fa-triangle-exclamation` | amber |
| `internal` | `module_json_missing`, `ErrInternal`, 5xx w/o body | `fa-server` | red |
| `network` | fetch threw (DNS/TLS/CORS/firewall) | `fa-plug-circle-xmark` | slate |
| `parse` | bad JSON, 200 OK missing `version` | `fa-file-circle-question` | slate |

Category names are snake_case on the wire and in CSS classes (`result-auth`,
`result-not_found`). Codes: API-CONTRACT.md → "Error code catalog".

**Token rotation:** old token returns `403 invalid_token/auth` at once. No
in-place repair: uninstall and reinstall via a fresh install URL. The version
pin survives rotation.

**Releases:** Actions → Release → Run workflow with the version (X.Y.Z).
`.github/workflows/release.yml` tags main and publishes the release with
generated notes and no attachments. Chronicle installs the source zip on Check
now (Admin → Packages) and its install hook writes the tag into `module.json`,
so the `version` on main is never read.

## Foundry conventions and footguns

- **ApplicationV2 `actions` delegates only `click`.** Wire other events in `_onRender` with `addEventListener`; adding them to `actions` is silently dropped.
- **Test bootstrap.** Importing `calendar-sync.mjs` (or anything pulling `settings.mjs` → `update-info.mjs`) in a unit test throws `ReferenceError: foundry is not defined`; stub `globalThis.foundry/game/Hooks` before the dynamic `import()`. Canonical stub: `tools/test-calendar-sync-visibility.mjs`.
- **i18n key collisions are silent.** Two `registerMenu` calls can't share an i18n key (Foundry returns the first match), and a menu's keys can't reuse a setting's namespace. Menus use `CHRONICLE.SettingsWindow.Menu*` and `CHRONICLE.Settings.UpdateInfo.*`.
- **Handlebars helpers need explicit registration** in `module.mjs`'s `init` (`eq`, `neq`, `lt`, `json`, `timeAgo`); register new ones there.
- **PARTS templates need exactly one root element.** `_parsePartHTML` rejects zero or several roots, only at `app.render()` time and depending on which `{{#if}}` branch fires. Wrap the body in one root so every branch emits one. Guard: `tools/test-template-roots.mjs` (recurses every branch).
- **`lang/en.json` can't mix a dotted-flat key with a sibling literal-key string.** `expandObject` throws when both `parent.X = "..."` and `parent.X.Y = "..."` exist and **rejects the whole lang file**: every `CHRONICLE.*` key then renders raw, with no lint error. Nest the option set under a sibling key (e.g. `VisibilityOption: {Visible, Hidden, Secret}`) and keep the label flat. Guard: `tools/test-lang-expand.mjs`.
- **JournalSync skips journals owned by another sync domain.** A journal with no `entityId` flag is pushed as a new page, so JournalSync skips `isCalendarNoteJournal` (our `calendarEventId` flag), `isOldNotesJournal` (`_notes-folder.mjs`) and `isMapJournal`, as `_isHandledByActorSync` does for characters. `tools/test-calendar-note-journal.mjs`.

## Architectural decisions

- **A-1 Chronicle-served distribution.** Chronicle serves release artifacts on a per-campaign signed URL, not GitHub Releases or Foundry's Package Repository: the operator pins campaigns to different versions and controls rollout from Chronicle's admin UI without public install URLs.
- **A-2 Descriptor-driven serving.** Chronicle reads `chronicle-package.json` from the release zip, falling back to defaults, so Chronicle stays generic and any Foundry module can register its own descriptor.
- **A-3 Foundry stores the Chronicle URL.** Foundry keeps the per-campaign manifest URL and checks it for updates, never GitHub, so the owner's version pin stays authoritative. Risk: Foundry's Package Repository also lists this module under its GitHub URL and may prompt to switch (README "Updating").
- **A-4 Update Source is a manual check.** It is a diagnostic, not part of the update loop: Foundry's Update All is the production path, and auto-correcting a deliberately GitHub-installed instance would be too aggressive.
